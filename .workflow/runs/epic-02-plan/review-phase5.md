# Requirements Review — Epic 2, Phase 5 (Reports, REP-01–REP-05)

## Recommendation

**APPROVED WITH FOLLOW-UPS.** The Phase 5 plan (`plan.md`, "## Phase 5 Implementation Plan — Reports", lines 431-492) is sound, ground-truth accurate, and does not re-litigate the already-resolved REP-04 projection formula. Every factual claim about existing models, services, and precedent code was checked directly against the codebase and is correct. However, unlike Phases 1-4 in this same document, the plan contains **no test-plan content whatsoever** (no "Planned touch points" table, no "Test plan" section), and several edge cases needed for a tester to write acceptance tests directly from the acceptance criteria are left implicit rather than stated. None of this blocks starting implementation, but the follow-ups below should be resolved — ideally by tech-analyst adding a short addendum to the plan — before pytest/Jest/Cypress cases are written against it.

## Ground-truth verification

Checked directly against `dojo-app/backend/app/models/__init__.py`, `balance_service.py`, `student_plan_service.py`, `contract_pdf_service.py`, `contracts.py`, and `StudentsPage.tsx`:

- **`Exam`/`ExamParticipant`/`ExamBoardMember`/`BeltPromotion`** (`models/__init__.py:466-543`) exist exactly as described. `ExamParticipant` carries `role` (`candidate`/`uke`), `status` (`pending`/`approved`/`rejected`), and the eligibility-override fields (`is_eligible`, `override_eligibility`, `override_reason`, `overridden_by`). `BeltPromotion` carries `student_id`, `belt_id`, `promoted_at`, `exam_id` (nullable FK back to `Exam`). `exam_service.py:248-275` (`promote_candidate`) confirms `exam_id=participant.exam_id` is set on promotion, so the plan's proposed join of `BeltPromotion` back to the specific `ExamParticipant`/`Exam` pair (by `student_id` + `exam_id`) is a real, well-formed join, not a guess — confirmed accurate.
- **`Attendance`** (`event_id`, `student_id`, `check_in_method`, `check_in_at`) joined to **`Event`** (`title`, `event_type_id`, `start_datetime`, `status`) and **`EventType`** (`name`) — all fields exist exactly as the plan states (`models/__init__.py:121-219`). Confirmed accurate.
- **`Payment`** (`payment_date`, `amount`, `status`) and **`StudentPlan`** exist as claimed (`models/__init__.py:336-407`). `StudentPlanService.get_current_price(db, student_id)` (`student_plan_service.py:34-37`) is confirmed present and unchanged, returning `active.plan_version.price` where `active = StudentPlanService.get_active(db, student_id)`; `get_active` (`student_plan_service.py:17-21`) filters `StudentPlan.status == "active"` — this matches the plan's stated projection logic ("summed across all students with an active `StudentPlan` whose `Student.is_active` is true") exactly.
- **`BalanceService.get_overdue_dashboard(db)`** (`balance_service.py:103-129`) is confirmed present and returns exactly the fields the plan cites: `student_id`, `student_name`, `registration_number`, `amount_owed`, `open_count`, `overdue_count`, `oldest_overdue_due_date`, `medical_exam_status` — accurate, and reusing it "unchanged" is a correct, low-risk design choice.
- **`contract_pdf_service.py`** confirmed to import `reportlab.platypus` (`Image`, `Paragraph`, `SimpleDocTemplate`, `Spacer`) and build a `SimpleDocTemplate(buffer, pagesize=A4)` — the "no new PDF library needed" claim holds; `platypus.Table`/`TableStyle` (needed for the new tabular renderer) are part of the same `reportlab.platypus` module already imported elsewhere in the dependency, so this is a correct precedent, not a stretch.
- **`contracts.py`'s `download_contract`** endpoint (lines 103-117) is confirmed to return a plain `Response(content=..., media_type=mime_type, headers={"Content-Disposition": f'attachment; filename="..."'})` with no `response_model` — exactly the pattern the plan proposes reusing for the new `format=pdf|csv` code paths.
- **`StudentsPage.tsx`'s `handleDownloadContract`** (lines 475-485) is confirmed to do `api.get(url, { responseType: 'blob' })` → `URL.createObjectURL` → synthetic `<a download>` click → `revokeObjectURL` — exactly as described, a valid reuse target for the new `ReportsPage.tsx`.

No factual claim in the plan needed correction. The "no new tables/migration" claim (acceptance criterion 6) is correct: every field and service the design relies on already exists, unmodified, from Phases 1-4.

## Findings

| # | Severity | Finding |
|---|---|---|
| 1 | MEDIUM | **No test-plan content at all.** Every prior phase in this document includes at least a one-line "Tests" row in a "Planned touch points" table (Phases 1-3), and Phase 4 goes further with a full pytest/Jest/Cypress breakdown ("### Test plan", lines 402-429). Phase 5's section has neither — no touch-points table, no test-plan subsection, nothing naming which pytest/Jest/Cypress cases will cover the 7 acceptance criteria. This is a structural regression relative to every other phase in the same plan, and it matters more here than it might elsewhere: this phase introduces two genuinely new rendering code paths (`render_csv`, `render_pdf_table`) with no existing test to model against (unlike, say, `render_pdf`'s magic-byte test in Phase 4, which this phase should explicitly say it reuses/extends). Per the repo's mandatory testing policy (`CLAUDE.md`: "All acceptance criteria must be covered by automated tests"), this should be filled in — at minimum: pytest for each `report_service.py` function (happy path + the not-found/empty-range cases below), a magic-byte/shape check for `render_pdf_table`'s output (reusing the `%PDF-` check style already used for `ContractPdfService.render_pdf`) and a content check for `render_csv`'s multi-section shape, Jest for `ReportsPage.tsx`'s four sections, and at least one Cypress case exercising a real PDF/CSV download end-to-end (mirroring `contracts.cy.ts`'s upload/download conventions). Not blocking for starting the service/API layer, but should exist before test-writing begins. |
| 2 | MEDIUM | **404 / not-found handling stated for only one of four report functions.** The plan explicitly states 404 handling for `get_belt_exam_report` ("404s ... if the student doesn't exist, mirroring `ContractService`'s existing not-found handling style") but is silent on the same behavior for `get_student_attendance_report` (invalid `student_id`), `get_class_attendance_report` (invalid `event_type_id`), and `get_financial_report` (no student-scoped lookup, so N/A there, but `months_ahead` validation is likewise unstated — see #5). None of the seven acceptance criteria mention 404 behavior either. A tester cannot write "request a report for a nonexistent student/event type" as a test case without this being stated. Recommend one sentence: all four report functions 404 the same way on an invalid FK-style ID (student_id, event_type_id), consistent with the belt-exam report's already-stated behavior. |
| 3 | LOW-MEDIUM | **Empty-result behavior (zero rows in range) is unspecified.** None of the acceptance criteria say what a report looks like when the date range or scope legitimately produces zero rows (e.g., a student with no attendance in the requested month, an `EventType` with no events in range). The obvious/expected answer — an empty list plus a zero total, HTTP 200, not an error — should be stated explicitly, since "empty report vs. error" is exactly the kind of ambiguity that produces divergent implementations and untestable criteria otherwise. |
| 4 | LOW | **REP-03's "per-student roster" scope is ambiguous.** "a per-student roster (student, total attendances in range) for that event type" doesn't say whether the roster includes every active student assigned to/eligible for that class type (showing `0` for non-attendees) or only students who attended at least once. This changes both the query shape and what a test fixture should assert. One line resolving this (recommend: only students with at least one attendance in range, since there is no "enrolled in this `EventType`" concept in the schema to define a zero-attendance roster against) would remove the ambiguity. |
| 5 | LOW | **Input validation edge cases unstated:** (a) `start_date > end_date`, (b) a non-numeric or negative `months_ahead`, (c) an unrecognized `format` value. FastAPI/Pydantic will likely reject malformed types automatically, but the *semantic* validation (date ordering, `months_ahead <= 0`) isn't addressed and isn't free from the framework. Not blocking — recommend a one-line default (e.g., 400 on `start_date > end_date`; `months_ahead` defaults/clamps to a minimum of 1) so these are testable rather than left to implementer discretion. |
| 6 | LOW | **No mention of row-count limits for large exports.** A dojo with years of attendance history exporting REP-02/REP-03 for a wide date range, or REP-04's payments section over a long range, has no stated upper bound. This is very likely fine for the epic's current scale and is explicitly non-blocking — flagging only so it's a conscious "no limit in this phase" default rather than an unconsidered gap, should data volume ever become a real concern. |

## Testability of the 7 acceptance criteria

Criteria 1 (REP-01), 4 (REP-04), 6 (no new tables), and 7 (authz) are concrete and directly testable as written — a tester can go straight from the criterion text to a pytest/API-test assertion. Criteria 2 (REP-02), 3 (REP-03), and 5 (REP-05) are testable for the "happy path" but only become fully testable once findings #2-#5 above are resolved (not-found handling, empty-range shape, roster scope, validation edge cases) — as currently worded, a tester would have to guess at expected behavior for those cases rather than read it off the plan, which is the same class of gap Phase 3's review flagged for its own edge cases (proration, allocation order) before those were written down explicitly.

## Completeness against REP-01–REP-05

Every requirement has a traceable design element and at least one acceptance criterion:

- REP-01 → `get_belt_exam_report` / AC1
- REP-02 → `get_student_attendance_report` / AC2
- REP-03 → `get_class_attendance_report` / AC3
- REP-04 → `get_financial_report` (reusing the already-settled projection formula) / AC4
- REP-05 → `report_export_service.py` (`render_csv`, `render_pdf_table`) + the `format=` query param on all four endpoints / AC5

No scope creep detected: the plan does not introduce any capability beyond REP-01–05 (no scheduling/emailing of reports, no new stored "report" entity, no student self-service — all consistent with the epic's Non-Goals and this phase's own explicit "instructor/admin only" default).

## Decision Gate — final

1. Ground-truth claims (model fields, `BalanceService`/`StudentPlanService` methods, `contract_pdf_service.py`'s ReportLab usage, `contracts.py`'s download-endpoint pattern, `StudentsPage.tsx`'s blob-download pattern) are all verified accurate — no correction needed.
2. **Finding #1 (missing test plan)** should be added as a short addendum before test-writing begins — not a schema/design change, just documentation of intended pytest/Jest/Cypress coverage, consistent with every other phase in this plan.
3. **Findings #2-#5** (404 handling for three of four report functions, empty-range shape, REP-03 roster scope, date/`months_ahead`/`format` validation) are small, one-line clarifications each, with obvious low-risk defaults suggested above — recommend tech-analyst fold these into the acceptance criteria text so they're testable as written, the same way Phase 3's edge cases (proration, FIFO allocation, grace period) were made explicit before build.
4. **Finding #6** (export row limits) is non-blocking; note only, no action required for this phase.

None of these findings rises to the level of Phase 2's genuinely blocking gap (a requirement with no schema concept to attach to) or requires a product-policy decision from the user — all six are plan-completeness/testability items that tech-analyst can resolve directly. This phase is approved to proceed; the follow-ups should be folded into `plan.md`'s Phase 5 section before acceptance tests are written against it.
