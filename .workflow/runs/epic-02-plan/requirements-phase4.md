# Requirements — Epic 2, Phase 4 (Contracts, CON-01–CON-04)

## Status

Draft for requirements-reviewer. Built on the epic-level policy already resolved on 2026-07-19 (`.workflow/epic-02/handoff.md` "Key Decisions"; `.workflow/runs/epic-02-plan/plan.md` "Contracts (Phase 4)" and the Phase 3 D11 breadcrumb). Those items are **settled inputs** and are not re-litigated below. This document breaks CON-01–CON-04 into concrete, testable requirements and separates them from a smaller set of genuinely open decisions the settled policy does not cover.

## Settled inputs (carried over, not re-decided here)

- Template versioning: the legal template is versioned; each generated contract records **both** the template version and the `PlanVersion` it used.
- Signature capture: dual path, operator's choice per contract — (a) on-screen/touch signature captured in-app and embedded into the generated PDF (tablet flow), or (b) upload of an externally-signed PDF, reusing the Phase 2 `Document` upload policy.
- Contract PDF must include: student data, plan, value ("valor"), and frequency (CON-02, literal requirement text).
- Non-goals (epic-wide): no online payment processing; no email/SMS/push notifications (Epic 3); no multi-organization configuration UI (Epic 4). Legal text/wording itself is a product/legal input, not an implementation assumption — this phase defines the *mechanism* for versioned templates, not the contract's actual legal copy.
- Cross-phase constraint (Phase 3 D11 breadcrumb, `plan.md` line 209): "Phase 4's implementation plan must account for [price-locking] by having its contract-generation/renewal workflow trigger `StudentPlanService.assign` with the current year's active tier version." This means contract generation is expected to be coupled to (not merely read-only against) plan assignment — see D1 below, which turns this breadcrumb into an explicit, confirmable trigger definition.

## Existing anchors in the codebase (read 2026-07-22)

- `Student` (`dojo-app/backend/app/models/__init__.py`) already has `contract_name`, `contract_cpf`, and a full address block (`address_street`, `address_neighborhood`, `address_city`, `address_zip`) — fields not used anywhere else in the codebase today. These appear to have been added in anticipation of exactly this phase: a contract's legal party data (full legal name and CPF may differ from the `full_name` used elsewhere for day-to-day display, and a mailing address is contract boilerplate, not needed for any other current feature). CON-02's "dados do aluno" should be read as pulling from these fields specifically, not just `full_name`/`registration_number`.
- `PlanTier`/`PlanVersion`/`StudentPlan` (Phase 3, shipped) already provide "plano, valor e frequência" exactly: `PlanTier.weekly_frequency`/`name`, `PlanVersion.price`, and `StudentPlan` as the student's locked, current assignment. `StudentPlanService.assign(db: Session, student: Student) -> StudentPlan` already exists and is the integration point the D11 breadcrumb points to — it takes no `tier_id` parameter; the tier is derived internally from `student.classes_per_week`, so there is no separate operator-facing "pick a tier" step to design around.
- `Document` (Phase 2, shipped) is already explicitly designed as a generic, reusable file-metadata table (`document_type: str`, not an enum) — its own docstring says "reused by medical exams and future document types." No schema change is needed to store a contract file; only a new `document_type` value ("contract") and a domain-level `Contract` record analogous to `MedicalExam` are needed.
- The Phase 2 handoff explicitly scoped its public self-service reversal to medical exams only: "This reverses the Phase 1-era blanket 'no student self-service' document-access note... that note now applies only to other future document types (e.g., contracts) unless separately revisited." Contracts are named there as the example of a document type that stays instructor/admin-only by default — see D5.
- No PDF-generation library, no on-screen-signature-capture library, and no "template management" UI pattern exist anywhere in the current stack (`dojo-app/backend/pyproject.toml`, `dojo-app/frontend/package.json` checked 2026-07-22). This phase is greenfield for both concerns; the requirements below intentionally do not name a specific library — that choice belongs to tech-analyst, not to this document.
- The frontend is React 19 + Vite + TypeScript (confirmed in `package.json`), consistent with the rest of the epic.

## Requirement-by-requirement breakdown

### CON-01 — Sistema gera contrato PDF no momento da matrícula

- **Actor:** instructor/admin triggers contract generation as part of enrolling or renewing a student — not a background/automatic process (no scheduler infrastructure exists anywhere in this codebase, per the Phase 3 precedent).
- **Central open question (D1):** what exactly is "o momento da matrícula"? Three candidate triggers exist in the current data model, and they are materially different in scope:
  1. **Student creation** — a brand-new `Student` row is created. Rejected as the sole trigger: a student can exist with no `StudentPlan` yet (Phase 3 confirmed `generate_monthly_charges` deliberately skips unassigned students), so a contract generated at this moment would have no plan/value/frequency to print, violating CON-02.
  2. **`StudentPlan` assignment/reassignment** (`StudentPlanService.assign`) — the moment a student is locked to a priced `PlanVersion`. This is the moment CON-02's required data (plan, value, frequency) first exists, and it is the exact integration point the Phase 3 D11 breadcrumb names for annual renewal.
  3. **A distinct, explicit "Gerar Contrato" action**, decoupled from plan assignment, that an operator invokes separately (possibly after first assigning a plan through the existing Phase 3 UI).
  - **Recommended default:** merge (2) and (3) into one action — an explicit "Matricular/Renovar aluno" workflow that, in a single transaction, both assigns/reassigns the `StudentPlan` (via the existing `StudentPlanService.assign(db, student)`, which already derives the tier automatically from `student.classes_per_week` — there is no manual tier-selection step to decouple) and generates the contract PDF referencing the resulting `PlanVersion`. This directly fulfills the D11 breadcrumb's literal wording ("trigger `StudentPlanService.assign`... as part of contract-generation/renewal") rather than leaving the two as separately-timed actions that could drift out of sync (e.g., an admin reassigns a plan but forgets to regenerate the contract, so the printed contract shows a stale price).
- **Not automatic on `Student` creation alone.**
- **Edge case:** if a student's `classes_per_week` has no matching `PlanTier` (the Phase 3 "plan-tier lookup gap" note), contract generation must fail loudly with the same error the underlying plan-assignment call already raises — not silently generate a contract with a missing/zero price.

### CON-02 — Contrato inclui dados do aluno, plano, valor e frequência

- **Data sourced directly from existing fields**, no new student-data collection needed: `Student.contract_name`/`contract_cpf`/address block/`birth_date`/`phone` (student), `PlanTier.name`/`weekly_frequency` (frequência), `PlanVersion.price` (valor) — all already modeled (see "Existing anchors").
- **Open question (D3):** the exact set of merge fields/placeholders available to a template author, and the substitution mechanism (e.g., `{{student.contract_name}}`), need an explicit, documented list before templates can be authored or tested — not specified anywhere in the raw CON-0X text. **Committed floor:** the field list is fixed now at CON-02's four data categories, expressed concretely — aluno: `Student.contract_name`, `Student.contract_cpf`, `Student.address_street`, `Student.address_neighborhood`, `Student.address_city`, `Student.address_zip`, `Student.birth_date`, `Student.phone`; plano: `PlanTier.name`; frequência: `PlanTier.weekly_frequency`; valor: `PlanVersion.price`. `birth_date` and `phone` were added to the required set per explicit user decision (2026-07-22) — both fields already exist on `Student` (currently nullable) and are now mandatory for contract generation, not merely available. Any additional fields (e.g., dates, dojo/instructor identity) needed once the actual legal text is drafted may be added later, but this list is the minimum viable, buildable-today set — not an open placeholder.
- **Edge case:** `contract_name`/`contract_cpf`/address/`birth_date`/`phone` fields are nullable today (no student currently has them populated, since nothing has required them until now). Generation must validate all of these — including `birth_date` and `phone` — are filled in before producing a contract, and surface a clear "complete the student's legal data first" error (naming the specific missing field(s)) rather than printing a contract with blank fields.

### CON-01 (template mechanism) — legal template versioning

- **Open question (D2):** who authors/edits template versions, and how? Two options:
  1. **Admin UI** — a simple versioned form structurally like `PlansPage.tsx`'s pattern for `PlanTier`/`PlanVersion` (a form that creates a new version and implicitly supersedes the previous one, following the `PlanVersion` append-only-supersession precedent): a text field holding the template body with placeholders, plus `effective_from`/`created_by` fields. Note `PlansPage.tsx`'s existing form only has `weekly_frequency`, `name`, `price` today — `effective_from`/`created_by` are proposed additions for the new template UI, not fields already present there.
  2. **Seed/config-only** — the template is a static asset committed to the repo and changed only via a code deploy.
  - **Recommended default:** admin UI (option 1), consistent with the `PlanVersion` precedent already established in this codebase, since legal wording is realistically going to need copy edits (typo fixes, legal review changes) without waiting for a deploy.
- Legal text content itself remains a product/legal input outside this document's scope (settled, carried over from `plan.md`).

### CON-03 — Sistema permite upload do contrato assinado/digitalizado

- **On-screen signature path:** the enrollment/renewal UI presents a touch/mouse-drawable signature pad (tablet-usable, consistent with the existing tablet check-in flow's device assumptions); the captured signature image is embedded into the generated PDF at signing time. The specific canvas/signature-capture library is a tech-analyst decision, not decided here — this document only states the user-facing capability required.
- **Upload path:** reuses the Phase 2 `Document` upload mechanism and policy exactly — same accepted MIME types, same size limit, same OCI Object Storage backend, same metadata-only persistence.
  - **Open question (D4):** should the accepted file types/size for a signed-contract upload be identical to Phase 2's policy (PDF/JPEG/PNG ≤10MB — the JPEG/PNG allowance exists there for a phone photo of a scanned paper document, "digitalizado" in CON-03's own wording implies exactly this use case) or narrowed to PDF-only for contracts specifically? **Recommended default: reuse Phase 2's policy unchanged** (PDF/JPEG/PNG ≤10MB) — no stated reason to diverge, and CON-03's own wording ("assinado/digitalizado") anticipates a scanned/photographed document, not only a clean PDF.
- **Operator choice:** per contract, the operator picks on-screen signature or upload — not both, not auto-selected. Once one path is used and the contract is marked signed, the other path is no longer available for that same contract record (prevents accidentally overwriting a completed contract).

### CON-04 — Sistema armazena contrato associado ao aluno

- **Data model:** a new `Contract` record (mirrors `MedicalExam`'s shape and lifecycle): `student_id`, `template_version_id`, `plan_version_id` (the two "which version was used" facts, both already committed as settled policy), `document_id` (nullable FK to the `Document` row holding the actual PDF bytes — generated-and-signed or uploaded, either way stored via the existing `Document`/OCI pattern), `signature_method` (`on_screen` / `uploaded`), `status`, `signed_at`.
- **Open question (D6):** does each annual renewal create a **new** `Contract` record that supersedes the previous one (append-only history, matching the `MedicalExam`/`StudentPlan` precedent exactly — a dojo needs to keep every year's signed contract, not just the latest), or does one `Contract` row get mutated/replaced at renewal? **Recommended default: append-only history**, exactly like every other versioned entity in this epic — a renewal creates a new `Contract` row tied to the new `StudentPlan`/`PlanVersion`, and the previous one is retained (status `superseded`), never deleted.
- **Open question (D7):** before a contract is signed, can a generated-but-unsigned draft be regenerated (e.g., to fix a typo in the student's address before printing) without creating a new formal history entry? **Recommended default:** a `Contract` is created in a `draft` status at generation time; regenerating a draft keeps the *same* `Contract` row (draft is a genuinely new mutable-pre-commit pattern, with no precedent elsewhere in this codebase — every other versioned entity here is append-only from creation); only the transition to `signed`/`active` (via on-screen signature or upload) is the point at which the record becomes permanent, append-only history per D6. This default resolves two sub-questions that were previously left implicit:
  - **(a) `Document` side:** regenerating a draft does **not** mutate the existing `Document` row in place. It creates a new `Document` row (the new draft PDF, `status = active`) and marks the previous draft's `Document` `superseded` — matching `Document`'s own established append-only/supersession pattern from Phase 2 exactly — and repoints `Contract.document_id` to the new row. The "mutable draft" behavior stays scoped to the new `Contract` concept only; `Document`'s existing contract is never broken.
  - **(b) Price re-lookup on regeneration:** regenerating a draft does **not** silently re-price against a possibly-updated `PlanVersion`. It preserves the originally-captured `plan_version_id` (and therefore price) from when the draft was first generated; only non-price fields (e.g., a corrected address) are updated. A genuine re-price only happens via an explicit re-run of the "matricular/renovar" action (D1), which re-derives the plan through `StudentPlanService.assign`. This matches D11's price-locking philosophy (a later catalog edit must never silently reprice an in-flight contract).
- **Open question (D5):** should a student be able to view/download their own stored contract via the same public registration+PIN self-service pattern Phase 2 established for medical exams? The Phase 2 handoff explicitly named contracts as the example document type that keeps the pre-Phase-2 "no student self-service" default unless separately revisited (see "Existing anchors"). **Recommended default: no — instructor/admin-only access**, same as Phase 3's financial data (D5 there), consistent with that note. Flagged explicitly because a student wanting their own contract copy is a plausible, real want, and the precedent that opened self-service for medical exams could reasonably be extended here if the user prefers.

## Proposed acceptance criteria (pending D1–D7 confirmation)

1. An instructor/admin can trigger a combined "matricular/renovar aluno" action (D1) that assigns/reassigns the student's `StudentPlan` and generates a contract PDF in one transaction, referencing the resulting `PlanVersion` and the currently active contract template version.
2. The generated PDF includes the student's legal contract data (`contract_name`, `contract_cpf`, address, `birth_date`, `phone`), the assigned plan's name/frequency, and its price (CON-02) — generation fails with a clear error, naming the missing field(s), if any required legal-data field (including `birth_date`/`phone`) is missing or if no `PlanTier` matches the student's `classes_per_week`.
3. Admin can author and version contract templates (D2) via a UI mirroring the existing `PlanVersion` pattern; each generated contract records exactly which template version and which `PlanVersion` it used (settled policy).
4. Per contract, the operator chooses one of two paths, mutually exclusive once signed: (a) an on-screen/touch signature captured in-app and embedded into the generated PDF, or (b) upload of an externally-signed/scanned PDF using the Phase 2 `Document` policy unchanged (D4).
5. Signed and generated contract files are stored via the existing `Document`/OCI Object Storage pattern (metadata + storage key only, no file bytes in the database), associated to the student through a new `Contract` record (CON-04) that also records template version, plan version, and signature method.
6. Contracts form an append-only history per student (D6): each renewal creates a new `Contract` record superseding the previous one; a pre-signature `draft` may be regenerated in place (D7) — regeneration supersedes/repoints the underlying `Document` (never mutates it in place) and preserves the originally-captured `plan_version_id`/price (never silently re-prices) — but a signed contract is never mutated.
7. Contract access (view/download) is instructor/admin-only (D5); no public/self-service endpoint is added for contracts in this phase.
8. No online payment processing, no email/SMS/push notifications, and no multi-organization template variance are introduced by this phase (carried-over Non-Goals).
