## 3. Gaps not captured in the draft

1. **Discounts — missing entirely, not even as an open decision (should be added, non-blocking).** `plan.md`'s own framing of what Phase 3 needs to define says: "Define plan/catalog ownership, billing cycle, due dates, pricing by weekly class frequency, partial/overpayment behavior, **discounts**, and overdue calculation." The settled "Key Decisions" resolved on 2026-07-19 cover everything in that list except discounts, and `requirements-phase3.md` doesn't mention the word once — not in the requirement breakdown, not as a D-item. This is a real discrepancy between what the epic's own plan said needed defining and what actually got carried into settled policy or flagged as open. Recommend adding it as an explicit open decision (e.g., D10) with a stated default of "no discount/scholarship modeling in this phase — the catalog is fixed-price only," since no FIN-0X item mentions discounts and the fixed-tier design is otherwise silent on per-student price overrides. This should be a one-line confirmation from the user, not a silent drop.

2. **Price change vs. existing contracts — missing, and it's a real cross-phase design fork (should be added, non-blocking but should be resolved before schema design, e.g. D11).** The draft correctly notes (as a settled, inherited constraint) that Phase 4 requires the plan catalog to be versioned because each contract records "which financial plan/version" it used. But it doesn't address what that versioning is *for*: when an admin updates a tier's price (creating a new catalog version), does an **existing** student's mensalidade auto-reprice to the new version next month (a live "current tier price" lookup, as FIN-02's breakdown literally describes: "looks up the price for the student's weekly-frequency tier from the versioned plan catalog"), or does an existing student's price stay locked to whatever version was active at enrollment/contract-signature (a "plan assignment" pinned per student, changed only by an explicit tier change)? These are materially different schemas: a live lookup needs only `Student.classes_per_week` + "current" catalog rows; a locked assignment needs a `student_plan_id`/`plan_version_id` foreign key set at enrollment and mutated only by explicit action. This also has a legal dimension the draft doesn't connect: if Phase 4 prints a specific price into a signed contract PDF "at enrollment," and Phase 3 silently re-prices that student when the catalog is later updated, the signed contract and the actual bill can drift apart — which is exactly the kind of thing a dojo owner or their lawyer would want to weigh in on rather than have decided by implementation default. Recommend flagging this explicitly, with a suggested default of **locked pricing per student/contract, changed only by an explicit re-enrollment or plan-change action** (grandfathering), since that's the more standard real-world contract behavior and gives the Phase-4-recorded "plan/version" an operational meaning beyond an audit label. Not blocking for starting analysis, but should be settled before `tech-analyst` commits to either schema shape, since reworking it later is more costly than the other D-items.

3. **Phase 5 (REP-04) dependency on a live price lookup — minor, non-blocking, worth one explicit sentence.** REP-04's projection ("sum of currently active plans" over the next N months) needs, for every active student, a way to know their current plan/price *without* a mensalidade record necessarily existing yet for future months (mensalidades are generated monthly, not months ahead). The draft's merged FIN-02/FIN-07 "price-for-tier" capability (acceptance criterion 1) is reusable for this, but the document never states this connection explicitly. Recommend adding one sentence tying REP-04's needs to the FIN-02/07 capability being callable independently of mensalidade-record existence, so `tech-analyst` designs it as a standalone query/service function from day one rather than accidentally coupling it to generated billing rows.

## 4. Internal consistency

- **FIN-02 vs. FIN-07 (D2):** The claimed redundancy is correct for the literal wording, and merging them for the *pricing* purpose (generate the mensalidade amount) is the right call — no reason to build the same lookup twice under two names. However, the draft's own alternate reading of FIN-07 (an audit comparing "should-pay under actual attendance" vs. "billed under declared tier") is a real, distinct capability that depends on D1's resolution. Recommend the merge stand as the default, but keep FIN-07's alternate reading as an explicitly named, deferred (not discarded) acceptance criterion, so that if the user resolves D1 toward attendance-derived frequency later, there's a clear home for it rather than having to re-derive it from scratch.

- **D3 vs. the Phase 2 handoff's actual wording (worth sharpening before this goes back to the user):** The Phase 2 handoff commits to more than a passive flag: "Blocking enforcement is deferred to Phase 3 (Financial foundation), which will define **the renewal/billing action that consults this status**" (`.workflow/epic-02/handoff.md`, MED-04 resolution). That phrasing implies Phase 3 was expected to define some *action* that consults the medical-exam status — plausibly, the monthly mensalidade-generation cycle itself, which is the only recurring "renewal" touchpoint that exists anywhere in this system (there is no separate enrollment-renewal entity, as Phase 2's own review confirmed). The draft's D3 answer — "no blocking action; surface the status as an additional flag alongside the overdue-payment flag" — is consistent with the epic's overall flag-only philosophy, but it quietly resolves "will define the renewal/billing action" down to "will not gate anything," without calling out that this is a *narrower* answer than what was previously promised. This isn't wrong as a default (it matches the epic's consistent no-blocking stance elsewhere), but the decision-gate item presented to the user should say explicitly: *"Phase 2 said Phase 3 would define an action that consults exam status; the recommended answer is that this action is a passive dashboard flag, not a gate on mensalidade generation — please confirm that's what you intended, since it's narrower than 'blocking enforcement deferred' might suggest."* This is a wording fix to how the decision is posed, not a new blocking requirement.
