# Requirements Review — Epic 2, Phase 2 (Exames Médicos + document foundation)

## Recommendation

**NOT ready for detailed implementation planning as literally written.** Two items need resolution before `squad-plan` can produce a testable Phase 2 plan: one is a product-policy clarification (MED-05 wording vs. resolved access policy — trivial, PM can confirm in one line), the other is a genuine open design question (MED-04's "matrícula renewal" has no existing attachment point in the schema) that needs tech-analysis, not just a product decision, since it may require a minimal new concept. Everything else below is scoped and testable once these two are closed.

## Findings

| Area | Finding | Planning response |
|---|---|---|
| MED-05 wording vs. policy | Requirement text says "Aluno/instrutor pode fazer upload," but the resolved policy is instructor/admin-only, explicitly no student self-service. Verified in code: students have no authenticated session at all — `auth.py`'s `OAuth2PasswordBearer`/`Token` flow issues tokens only to `User` (instructor/admin); the student-facing `registration_number`+PIN pattern (`checkin.py`, `pre_checkins.py`) is a per-request, stateless credential check with generic non-disclosing responses, used only for read/confirm actions, never authenticated file upload. There is no technical path for a student to authenticate and upload today. | MED-05 as literally written is not achievable under the resolved policy. Practical resolution: instructor/admin uploads the exam PDF/image on the student's behalf (student hands over a physical or digital copy). PM should confirm this substitute wording with the user before build; requirements text should be corrected to "Instrutor/admin faz upload do PDF do exame médico do aluno," not left ambiguous. |
| MED-04 "matrícula" attachment point | "Bloqueia renovação de matrícula" presupposes a renewal/enrollment-cycle event. Checked schema: `Student` has `is_active` (boolean flag), `contract_name`, `contract_cpf`, `classes_per_week`, but no `Enrollment`/`Membership`/renewal/cycle entity anywhere in `models/__init__.py`. Checked `students.py` API: only `create`, `update` (PUT), and `deactivate` (soft delete via `is_active=False`) exist — no reactivate/renew endpoint, no enrollment period, no date range. "Matrícula" has no current system representation beyond the student record's existence and its active flag. | Genuinely unresolved from a requirements standpoint — not a wording fix. Two candidate resolutions exist and are architecturally different: (a) block reactivation of an inactive student (repurpose `is_active` toggle as the "renewal" moment) — minimal, but doesn't cover an active student whose exam lapses mid-membership; (b) Phase 2 must define a minimal explicit "renewal" touchpoint (e.g., a manual renew action/endpoint, or gating an existing action like contract regeneration in Phase 3/4) so MED-04 has an event to intercept. Flag for tech-analyst: needs a design decision on what "matrícula renewal" means operationally in this codebase before an endpoint/test can be written. Do not let Phase 2 silently narrow "renovação de matrícula" to student reactivation without an explicit product decision, since that would silently drop coverage for the (likely more common) case of an active student's exam expiring. |
| MED-03 "alert" mechanics | "Alerta quando exame está próximo do vencimento (30 dias)" is not further specified. Epic Non-Goals already exclude email/SMS/push in this epic (Epic 3 territory per plan.md), so the only remaining candidate is a visual/dashboard flag (e.g., a status field or badge on the student record/list), not a notification. | Should be stated explicitly as an acceptance criterion: a computed status (e.g., `valid` / `expiring_soon` / `expired`) surfaced in instructor-facing student views, no push/email. No product ambiguity remains once this is written down — recommend PM add the sentence to the phase's acceptance criteria for testability, not a blocking gap. |
| MED-01/02 data shape | Not specified whether "exam" carries any medical content fields (e.g., doctor's name, restrictions) beyond a date + file. Roadmap's UI hint ("Exam date picker, upload interface") suggests only a date is structured; the PDF/image itself is opaque. | Should be confirmed as: one structured field (exam date) plus one opaque attached document; no other medical data modeled. If correct, no gap — just needs an explicit line in the phase scope so it isn't reinterpreted as a richer medical record. |
| Exam model conflation risk | The existing `Exam`, `ExamParticipant`, `ExamBoardMember` models (in `models/__init__.py`) model **belt promotion exams** (exam board, candidates/ukes, eligibility overrides) — a different concept from a **medical exam** document (a dated health-clearance record with an attached file). Confirmed these must not be reused or extended for MED-01–06; Phase 2 needs its own model(s) (e.g., a medical-record/document entity keyed to `Student`), unrelated to `exams`/`exam_participants`. | No requirements gap, but worth stating plainly as an explicit non-goal/clarification so the implementation phase doesn't attempt to bolt medical fields onto the belt-exam tables. Tech-analyst should design a new model, not extend `Exam`. |
| Reporting order | REP-01 ("Relatório de exame de faixa exportável por aluno") is a **belt**-exam report (Phase 4/Reports), unrelated to Phase 2's medical documents. Confirmed via `.planning/REQUIREMENTS.md` traceability table (REP-01 to REP-05 → Phase 4) and roadmap Phase 4 goal text. | Correctly out of scope for Phase 2; no action needed beyond confirming it stays excluded — already reflected in `plan.md`'s phase ordering. |
| Document-storage reuse scope | Phase 2's deliverable is explicitly "reusable controlled PDF storage pattern" for later reuse by Phase 3/4 (Contracts) per `plan.md`. Access/storage/retention policy is already resolved (OCI Object Storage, metadata-only persistence, instructor/admin-only, PDF/JPEG/PNG ≤10MB, soft delete + audit trail). | No gap — policy is sufficiently concrete and testable as stated in `handoff.md`/`plan.md`. Tech-analyst can proceed straight to designing the generic document abstraction once the two items above are resolved, since the abstraction's shape (owner type, doc type, key, audit fields) doesn't depend on how MED-04 is resolved. |

## Decision Gate

1. **Product decision (PM, quick):** Confirm MED-05's actual actor is instructor/admin-only (student hands over the exam; instructor/admin uploads on their behalf), and correct the requirement wording accordingly.
2. **Tech-analysis (not a pure requirements call):** Define what "renovação de matrícula" means operationally given no existing enrollment/renewal entity — decide between (a) gating student reactivation via `is_active`, or (b) introducing a minimal explicit renewal touchpoint/endpoint that MED-04 can block. This determines whether Phase 2 needs a new concept beyond documents+medical dates.
3. **Acceptance-criteria wording (PM, quick):** Make MED-03's "alert" explicit as a visual/dashboard status flag (no email/push, consistent with Non-Goals), and confirm MED-01/02's exam record is date-only plus attached file (no further medical fields).

Once (1) and (3) are written down and (2) has an answer, Phase 2 is ready to hand to `tech-analyst` for detailed technical planning.
