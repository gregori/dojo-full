# Requirements Review — Notification Hub (Student Opt-In, Delivery & History) (NH-01 – NH-10)

## Recommendation

**APPROVED WITH FOLLOW-UPS.** All ten acceptance criteria are stated as concrete Given/When/Then statements that name the exact model fields, statuses, and thresholds they key off, and every one of them is testable without guessing at implementation. The document correctly treats the six already-locked product decisions (channels, recipients, opt-in mechanism, trigger lead times, one-time firing, no backfill) and the NH-03 eligibility rule / all-event-types trade-off as non-negotiable — this review does not re-litigate any of them. Every ground-truth citation in the document (file paths, line numbers, field names, service/method names) was independently re-checked against the current codebase and is accurate down to the line number.

Three narrow, non-blocking items are worth a one- or two-sentence tightening pass, either by `product-manager` before handoff or directly by `tech-analyst` during design. None of them contradicts anything already decided, and none requires reopening the locked decisions or a fresh user interview.

## Findings

| # | Severity | Finding |
|---|---|---|
| 1 | Non-blocking, fix directly | **NH-01's third criterion (line 62) cross-references the wrong requirement ID.** It reads "...they may still access their in-app notification history (NH-05) using the same `registration_number` + `pin`" — but NH-05 is the *Mensalidade due reminder trigger*, not the in-app history feature. In-app notification history is defined in **NH-08**. The intended meaning is unambiguous from surrounding context (the sentence is clearly about viewing notification history), so this doesn't block understanding today, but a stray wrong ID in a requirements doc is exactly the kind of thing that causes downstream confusion once `tech-analyst`/QA start writing traceability matrices or test-case IDs keyed to "NH-0X". **Fix guidance:** change "(NH-05)" to "(NH-08)" on line 62. One-character-class fix. |
| 2 | Non-blocking, recommend one sentence | **No criterion or Non-Goal addresses whether a student/guardian can revoke or unsubscribe from push notifications from within the product itself**, as distinct from revoking browser-level notification permission (which the app has no control over and which NH-09 already acknowledges via its "best effort"/"subject to the browser/OS" framing). The Explicit Non-Goals section is otherwise unusually thorough — it explicitly rules out dedup, escalation/re-sends, admin recipients, other channels, a login system, and a guardian data model — but says nothing about in-app opt-out. This isn't a re-litigation of any locked decision (opt-out was never mentioned as decided either way in the "Decision already locked in" section), so it reads as a genuine gap rather than an intentionally-deferred item. It does not block moving to `tech-analyst`, since none of the ten NH-0X criteria claim to cover unsubscribe and none would need to be rewritten regardless of the answer — but it should be resolved with one explicit sentence before or during design, since it is a real (if small) product-scope question, not a pure implementation detail. **Fix guidance:** add one sentence to Non-Goals, either declaring in-app unsubscribe out of scope for v1 ("students rely on revoking browser notification permission directly; no in-app 'stop notifications' control is provided in v1") or adding a minimal NH-11 criterion if the user actually wants one. Either is a one-round, non-blocking product-manager touch-up, not a full re-interview. |
| 3 | Non-blocking, optional | **NH-03's eligibility rule is described as sourced entirely from `_validate_eligibility`, but the `is_active` half of the combined rule actually lives in the separate `authenticate_student` function** (same file, a different code path used only during interactive/authenticated pre-check-in, not by `_validate_eligibility` itself). The *behavior* the document describes is accurate — see Ground-truth verification above — this is purely a citation-precision nit, not a testability or clarity gap in the criterion text itself (the criterion states the combined rule in full, self-contained prose, so an implementer doesn't need the citation to be exact to build or test it correctly). **Fix guidance:** optionally clarify the citation to something like "eligibility combines the `is_active` check from `authenticate_student` (same file) with the belt-eligibility check from `_validate_eligibility` (lines 46-51)" — purely cosmetic, safe to skip entirely. |

## Testability assessment, item by item

- **NH-01 (opt-in page):** Testable — three Given/When/Then branches (match+grant, no-match, match+decline) cover the full decision tree with concrete, checkable outcomes (subscription created and linked to `student_id` / clear error, no subscription / clear message, in-app history still reachable). One ID typo noted (Finding #1), doesn't affect the criterion's own testability.
- **NH-02 (multi-device, no dedup):** Testable — states a clear non-requirement ("not required to detect or replace") as an explicit negative, which is itself assertable (a test can confirm two subscriptions coexist for one student without asserting any dedup happened). No gap.
- **NH-03 (pre-check-in trigger):** The most detailed criterion in the document and the most rigorously testable — five separate Given/When/Then branches covering the happy path, belt-ineligibility, already-confirmed/converted, cancelled event, and cancelled-pre-check-in-is-not-confirmed edge cases, each independently verified against real model/service code above. No gap.
- **NH-04 (medical exam trigger):** Testable — three branches (fires at 30 days for `active`, does not fire for `superseded`, does not fire for no-exam-on-file). All three statuses verified to exist exactly as named. No gap.
- **NH-05 (mensalidade trigger):** Testable — two branches (fires regardless of partial payment, does not fire once fully `paid`), both verified against `BalanceService.compute_status`'s actual precedence (`paid` checked first, before `overdue`/`partial`/`open`). No gap.
- **NH-06 (one-time firing):** Testable as a negative assertion ("no duplicate... ever") — requires the implementation to persist a per-occurrence firing record, which is correctly left as a `tech-analyst` decision while the product requirement itself (idempotent-per-occurrence) is unambiguous. No gap.
- **NH-07 (no backfill):** Testable — concrete go-live-relative framing with three worked examples (past-due event, already-expiring exam, already-overdue mensalidade). No gap.
- **NH-08 (in-app history + read state):** Testable — minimum-field list is concrete (type, message, generated date, read state) and the cross-device read-state persistence requirement is explicit and checkable (mark-as-read from one device, verify from another). No gap.
- **NH-09 (push delivery):** Testable — both the has-subscriptions and zero-subscriptions branches are covered, and the criterion correctly scopes the app's responsibility to "send attempt" rather than guaranteeing OS/browser delivery (an honest, checkable boundary rather than an untestable absolute). No gap.
- **NH-10 (content):** Testable — each of the three message types has a concrete, minimum content list (event title+datetime, exam expiration date, mensalidade reference month+due date). No gap.

**Explicit Non-Goals / Constraints / Open Questions sections:** all consistent with the ten criteria and with each other; no scope-creep risk found. The Constraints section's computed-on-read caveat is an accurate, correctly-flagged implementation constraint (verified above: none of `PreCheckIn`, `MedicalExam`, or `Mensalidade` has a stored status column that "flips" at the right moment). The Open Questions section correctly identifies four genuinely-technical, non-product-ambiguous items (push provider/library, scheduling mechanism, API shapes, subscription-staleness cleanup) — confirmed accurate on independent review, not just asserted. The one gap this review found (Finding #2, in-app unsubscribe) is not listed in Open Questions and should be, or resolved directly, before this is considered fully closed.
