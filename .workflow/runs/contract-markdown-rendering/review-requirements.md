# Requirements Review — Contract Template Markdown Rendering (CTM-01 – CTM-10)

## Recommendation

**NOT APPROVED.** One blocking gap: CTM-06 only closes half of the injection surface it names. It requires escaping merged data against **ReportLab XML markup** (`<`, `>`, `&`) but says nothing about shielding merged data from being interpreted as **Markdown syntax** (`*`, `_`, `#`, `-`, `---`) by the very parser CTM-03 requires to run *after* the merge. Given this feature's locked-in merge order (Jinja2 first, Markdown-parse second — CTM-03, "hard constraint, not a design suggestion"), a student/plan field that happens to contain a Markdown-special character is exposed to the Markdown parser exactly the same as the admin's own hand-authored syntax, with no criterion telling the implementer this must not happen. This is not a hypothetical: it is the same class of miss that produced the HIGH finding in `report_export_service.py` (`.workflow/epic-02/pr-5-reports/review.md`), just one layer up the pipeline (Markdown-syntax injection instead of ReportLab-XML injection), and — because it can silently corrupt formatting rather than crash — it is arguably worse in this feature's context (a legal contract that gets signed) than a loud 500.

This is a single, scoped, one-paragraph fix to CTM-06 (plus a short CTM-05 clarification of how the two criteria interact). Everything else in the document — the Markdown subset table, CTM-01/02/03/04/07/08/09/10, the Constraints and Non-Goals sections — is clear, complete, testable, and consistent with the codebase's ground truth. Do not re-open the Option A architecture decision or the merge-order decision; both are compatible with the fix below.

CTM-06's claim that this is a real, pre-existing gap (not new, not invented) is correct.
- `dojo-app/frontend/src/pages/ContractTemplatesPage.tsx:89-96,202-203` confirms the plain `<textarea>` authoring and `whitespace-pre-wrap` preview described in "Context" are accurate as of this diff.
- `dojo-app/backend/app/services/contract_pdf_service.py:42-63` (`build_context`) confirms `student.address` is a *server-built* string (`f"{street}, {neighborhood}, {city} - {zip}"`) — i.e. a merged field can itself already contain a bare, mid-string `-`/`,` sequence assembled from free-text student data (`address_street`, `address_neighborhood`), not just single scalar values. This strengthens the CTM-06 finding below: the merge surface isn't limited to short atomic tokens like a name, it includes a concatenated multi-part string built from several free-text DB columns.
- `dojo-app/backend/tests/unit/test_contract_pdf_service.py` confirms today's only two test bodies are trivial (`"Contrato de {{ student.contract_name }}.\n\nPlano: {{ plan_tier.name }}."` and `"Corpo do contrato."`) — no existing fixture exercises a merge value containing Markdown- or ReportLab-special characters, so nothing here already covers the gap.
- `.workflow/epic-02/pr-5-reports/review.md` confirms the precedent cited in CTM-05/CTM-06 accurately: the HIGH finding was exactly "DB-sourced free text with no character restriction, entered by a trusted actor (instructor/admin), reaching a `Paragraph()` unescaped" — the same actor/trust profile as this feature's `Student`/`PlanTier`/`PlanVersion` fields.

No factual claim in `requirements.md` needed correction.

## Findings

| # | Severity | Finding |
|---|---|---|
| 1 | **BLOCKING** | **CTM-06 escapes merged data against ReportLab-XML injection but not Markdown-syntax injection, even though CTM-03 mandates the merged text be Markdown-parsed.** Concretely: if `student.contract_name`, `student.address` (itself a concatenation of `address_street`/`address_neighborhood`/`address_city`/`address_zip`, all free-text DB columns — see ground-truth note above), `plan_tier.name`, etc. contain a `*`, `_`, `#`, or a line that after merge begins with `-`/`1.`/`---`, the Markdown parser required by CTM-03 has no way to know that text came from a merge field rather than the admin's own authored Markdown, and per CTM-03's locked merge order it sees exactly the same string either way. A stray `*` in one merged field can pair with a stray `*` anywhere else later in the same document and open an unbalanced-bold span that silently reformats or swallows unrelated, legitimate contract text — a **content-corruption** failure mode, not a crash, so it would not even be caught by CTM-05's "never raises an exception" test and could go unnoticed until a signed contract is read closely. CTM-06 as written ("literal ReportLab-markup-special characters... present in Jinja2-merged... data are escaped before ReportLab inline markup... is applied") only names the ReportLab-XML half of the injection surface (`<`, `>`, `&`) and explicitly scopes itself to "before ReportLab inline markup is applied" — it does not say merged values must also be prevented from being *recognized as Markdown syntax* in the first place. **This is fixable without touching the locked merge order or the Option A architecture**: e.g., require that merged field values are neutralized against the supported Markdown-special-character set (via Markdown's own backslash-escape convention, or by having the converter escape/skip Markdown-syntax detection specifically inside Jinja2-substituted spans) before the fully-merged text is handed to the Markdown parser — this still happens "after Jinja2 substitution, before/during Markdown parsing," consistent with CTM-03. Fix: extend CTM-06 to state explicitly that merged placeholder values must render as literal text with respect to **both** ReportLab markup **and** the supported Markdown subset — a merge value containing `*`, `_`, `#`, or a leading `-`/`1.`/`---` must never produce bold/italic/heading/list/hr formatting, only literal characters — and add at least one dedicated acceptance/test case for this (e.g. a student name or plan name containing `*` or `_` must render as the literal character, not trigger emphasis, and must not "bleed" formatting into subsequent unrelated paragraphs). |
| 2 | Non-blocking, fold in at same time | **CTM-05's "best-effort" hedge softens an otherwise-good, concrete criterion.** The three worked examples (unclosed `**bold`, `###`+ heading, nested list item) are genuinely testable as written — good, specific, matches the "graceful degradation, not exception-avoidance-only" bar this codebase's precedent requires. But the parenthetical "(best-effort — e.g. ...)" reads as illustrative-only rather than binding, which could let an implementer treat the exact fallback rendering as optional so long as nothing crashes. Recommend dropping "best-effort" and stating the three examples as the required behavior (or, if genuine per-case flexibility is intended, say so explicitly and state what is *not* acceptable, e.g. "must not silently drop the offending text entirely"). |
| 3 | Non-blocking, fold in at same time | **CTM-05/CTM-06 interaction is unstated.** Once CTM-06 is fixed per finding #1, a merged field containing e.g. an unbalanced `*` needs a single unambiguous rule for which criterion governs it: it should never even reach CTM-05's "malformed input" fallback path, because CTM-06's escaping should prevent the Markdown parser from ever seeing it as syntax in the first place. Worth one sentence in the document clarifying that CTM-06 (merge-field literal-rendering) takes precedence over / runs prior to CTM-05 (malformed-admin-Markdown fallback) so an implementer doesn't need to re-derive the ordering themselves. |
| 4 | Non-blocking, fold in at same time | **CTM-04's regression-test anchor is vague on which "real existing template body" to use.** "Covered by a regression test using at least one real existing template body" doesn't say whether that means a body pulled from an actual DB/seed row, or the trivial inline fixtures already in `test_contract_pdf_service.py` (`"Contrato de {{ student.contract_name }}.\n\nPlano: {{ plan_tier.name }}."`). The latter are fine as a literal backward-compat baseline (confirmed they exist, see ground-truth above) but naming them explicitly (or stating "any pre-existing plain-text fixture, e.g. the ones already in `test_contract_pdf_service.py`, is sufficient") would remove implementer guesswork. |
| 5 | Non-blocking, optional | **Two small Markdown-subset-boundary questions are left implicit**, not currently blocking anything but worth a one-line answer while the document is being touched anyway: (a) does `**text**` combined with `_text_` nest (e.g. `**_bold italic_**`) or is combined emphasis out of scope like heading-3+/nesting is for lists? (b) is a literal, admin-intended `*`/`#`/`-` character (not merge-field-originated) escapable via a leading backslash, matching common Markdown convention, or is there no admin-facing escape mechanism at all (meaning a non-technical admin who wants to literally start a line with `-` has no way to avoid it becoming a list)? Neither blocks approval — CTM-09 already leaves parser mechanics to `tech-analyst` — but both are cheap to settle now rather than have `tech-analyst` guess.

## Testability assessment, item by item (per the specific questions posed for this review)

- **CTM-05 testable as written?** Yes, with the "best-effort" hedge tightened (finding #2) — the three concrete examples give an implementer/tester exactly what to assert (no exception raised, valid PDF bytes returned, specific fallback rendering per case).
- **CTM-06 precise enough to act on without re-deriving the threat model?** No — this is the blocking finding. As written it correctly identifies and closes the ReportLab-XML half of the threat (matching the `report_export_service.py` precedent almost verbatim), but it does not identify the Markdown-syntax half of the same threat, even though CTM-03's locked merge order creates exactly that exposure. An implementer following CTM-06 literally would escape `<`/`>`/`&` in merged values and reasonably believe the merge-field injection risk was fully closed — it would not be.
- **Is the Markdown subset boundary unambiguous and complete enough to implement/test against?** Yes for the eight listed elements and their explicit non-goals (h3+, nesting, links/images/tables/code/blockquotes) — the italic-vs-list-marker `_`/`*` disambiguation is a good example of the document proactively resolving an ambiguity rather than leaving it implicit. Two minor open questions noted in finding #5 (non-blocking).
- **Is CTM-04 backward compatibility a concrete testable case?** Yes, the assertion ("continues to render identically... no unexpected headings/bold/lists/rules") is concrete and testable; only the specific fixture-body reference is vague (finding #4, non-blocking).
- **Does CTM-09 leave tech-analyst enough constraint?** Yes — "small, fixed 8-element subset, avoid an unjustifiably heavy dependency, hand-rolled vs. a light package like `markdown` is tech-analyst's call" is an appropriately-scoped constraint, consistent with how CTM-09 itself frames the decision as intentionally left open. No gap found here.
