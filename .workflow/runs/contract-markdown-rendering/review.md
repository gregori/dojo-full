# Independent + Security Review — Contract Template Markdown Rendering (CTM)

## Verdict: NOT APPROVED — 1 HIGH content-integrity finding (empirically reproduced), plus LOW observations

The HIGH finding directly breaks **CTM-06(b)** — the requirement's own headline guarantee that a Jinja2-merged field's stray Markdown-special character "must never combine with Markdown syntax located elsewhere in the document to produce unintended formatting." The escape/unescape mechanism (`escape_context` + `_inline`'s backslash-marker scheme in `markdown_pdf.py`) does **not** hold in the most natural, foreseeable authoring pattern for this feature — an admin wrapping a placeholder in real `**bold**`/`_italic_` markup to emphasize a name (e.g. `"**{{ student.contract_name }}**"`) — nor, for underscores specifically, even when the merge field and the real markup are simply in the same paragraph at all, adjacent or not. This is not a contrived adversarial payload; `contract_name`/`address`/etc. are free-text DB columns with no character restriction, and bolding a placeholder is an ordinary, expected use of the feature this PR ships. None of the 5 new `TestToFlowablesMergeFieldLiteralRendering` tests catch it because they place the merged value in either a separate paragraph block or a bare (non-wrapped) position — the one combination that actually breaks (merge field immediately touching/wrapped by the same-type real delimiter) is untested.

## Findings (ranked, most severe first)

### 1. [HIGH — Content-integrity, breaks CTM-06(b) for realistic merged data] The backslash-escape/unescape mechanism does not prevent a merged field's escaped Markdown-special character from pairing with a real, admin-authored delimiter of the same type, producing a leaked literal backslash and a corrupted/mis-paired emphasis span

**Root cause** (`dojo-app/backend/app/services/markdown_pdf.py:21-37`): `_BOLD_RE = re.compile(r"\*\*(?<!\\\*\*)(.+?)\*\*")` only guards against the specific 3-character sequence `\**` immediately preceding an opening `**`; it does nothing to stop its own non-greedy `(.+?)` capture from later consuming one half of an escaped `\*` sequence and pairing the surviving lone `*` with a real, unrelated `**`/`*` elsewhere in the block. `_ITALIC_RE = re.compile(r"_(.+?)_")` has **no** escape-awareness at all — any single stray underscore anywhere in a block is eligible to pair with the *next* underscore found, regardless of source (admin-typed or merged).

**Empirically reproduced** (throwaway scripts against the actual module, not reused from the implementer's tests):

```
context = MarkdownPdfConverter.escape_context({"student": {"contract_name": "Silva*"}})
template = "**{{ student.contract_name }}**"     # admin bolds a placeholder — the ordinary use case
merged = Template(template).render(**context)     # -> '**Silva\\***'
MarkdownPdfConverter.to_flowables(merged)[0].text  # -> '<b>Silva\\</b>*'
```

Result: a literal backslash character leaks into the visible rendered paragraph (`Silva\`), the `<b>` tag closes one character early (only "Silva\" is bolded), and a bare `*` is left dangling immediately after `</b>` — not literal text, not correct bold, an actively corrupted/mis-paired span in what would be a signed legal contract. Further reproduced variants, all broken the same way: `contract_name = "*Silva"` with template `"**{{ ... }}**"` happens to survive intact (backslash+asterisk stay adjacent), but `"Sil*va"`, `"**"`, and `"*"` alone all produce leaked-backslash/mis-paired output when wrapped in real `**...**`.

The italic case is strictly worse and does **not** require the merge field to be wrapped by the real markup — merely present in the *same paragraph block* is enough, because `_ITALIC_RE` has no escape guard whatsoever:

```
context = MarkdownPdfConverter.escape_context({"student": {"contract_name": "Silva_"}})
template = "Nome: {{ student.contract_name }} texto _italico_ fim."   # merge field NOT adjacent to the real _..._ span
merged = Template(template).render(**context)  # -> 'Nome: Silva\\_ texto _italico_ fim.'
MarkdownPdfConverter.to_flowables(merged)[0].text
# -> 'Nome: Silva\\<i> texto </i>italico_ fim.'
```

This is a textbook instance of the exact failure mode CTM-06(b) names as the required guarantee to prevent ("a stray `*` inside a merged field must not pair with a `*` elsewhere in the template body to open an unintended bold/italic span") — reproduced with underscore, and reproduced for bold when the placeholder is wrapped in real bold, which is the single most natural way an admin would emphasize a name in a template.

**Why the test suite didn't catch it** (`dojo-app/backend/tests/unit/test_markdown_pdf.py:147-183`): `test_merged_asterisk_renders_literally_and_does_not_bleed_into_other_bold` and `test_merged_underscore_renders_literally_and_does_not_bleed_into_other_italic` both place the merged value and the real `**negrito**`/`_itálico_` span in **separate, blank-line-separated paragraph blocks**. Because `to_flowables` splits on blank lines (`re.split(r"\n\s*\n+", text)`) *before* `_inline()` ever runs, this separation trivially prevents any cross-block pairing regardless of whether the escape mechanism itself works — the tests prove a weaker property (block-splitting isolates blocks) than what CTM-06(b) actually requires (a merge field's special character is inert with respect to Markdown syntax "elsewhere in the document," which naturally includes the same paragraph, and especially includes the placeholder being wrapped directly in real markup — the paradigm authoring pattern this whole feature exists to support, i.e. `"**{{ student.contract_name }}**"`). No test in `test_markdown_pdf.py` or `test_contract_pdf_service.py` places a merge-field special character in the same block as, let alone directly wrapped by, a real same-type delimiter.

**Fix guidance:** the current mechanism (single backslash prefix + a partial 3-char negative lookbehind on bold only) is not sufficient. A robust fix needs the bold/italic regexes to never treat an escaped-marker's surviving character as a real delimiter candidate at all — e.g. use a placeholder sentinel string (not a bare backslash + the literal character) for escaped chars in `escape_context`, run `_BOLD_RE`/`_ITALIC_RE` against text that has no raw `*`/`_` characters left over from escaping, and only substitute the real literal character back in as the very last step. Alternatively, escape to a form that cannot itself contain a bare `*`/`_` (e.g. a temporary non-printable/rare Unicode marker character unlikely to appear in admin-authored Markdown, swapped back to the literal character after `_inline()`'s regex passes complete). Add regression tests for: (a) a merge field wrapped directly in admin-authored `**{{ field }}**`/`_{{ field }}_` where the field value ends or starts with the corresponding special character; (b) a merge field's stray special character in the same paragraph block as, but not adjacent to, an unrelated real span of the same type.

### 2. [LOW — latent, non-blocking] `escape_context` has no `list` branch

`markdown_pdf.py:49-59`'s `escape_value` only branches on `isinstance(value, dict)` / `isinstance(value, str)`; a `list` leaf (e.g. a future context value that's a list of dicts or strings) would fall through to the final `return value` unchanged, silently skipping escaping for any strings nested inside it. Not currently reachable — `ContractPdfService.build_context` (`contract_pdf_service.py:44-64`) only ever produces `dict`/`str`/`int`/`float`/`None` leaves, confirmed by direct read — so this is not a live bug today, but it is an unguarded gap that would silently reopen CTM-06 the moment any future context field became a list (e.g. an itemized plan-features list). Worth a one-line `isinstance(value, list)` branch (`[escape_value(v) for v in value]`) for defense-in-depth, consistent with the "total function" design already used everywhere else in this module, but not blocking since no current code path triggers it.

### 3. [LOW — documented, accepted, non-blocking] Leading `"N. "` merge-field values not escaped

Already self-disclosed in `plan.md`'s "Risk assessment" and in the implementer's handoff — a merged value starting with a digit-dot-space pattern (e.g. a contrived `"1. Nome"`) is not defensively escaped and could theoretically be read as an ordered-list marker if it lands at the very start of a block. No realistic trigger in current student/plan data (names, addresses, CPFs, currency, dates). Consistent with the requirements' own explicit non-goal framing; not re-flagged as blocking.

### Finding 1 (HIGH — CTM-06(b), merged special character pairing with real markup) — FIXED, independently confirmed structural, not just empirical

- Read `markdown_pdf.py:36-77` directly. `_SENTINELS` maps `*`/`_`/`#`/leading-`-` to four distinct Private Use Area code points (confirmed via direct byte inspection: `U+E000`–`U+E003`). `escape_context`'s `escape_value` (str branch, lines 70-76) does a global, unconditional `str.replace(char, sentinel)` for every occurrence of `*`/`_`/`#` in the leaf value (not just the first), plus a separate leading-`-`-only check — this is unconditional and complete for every occurrence in a leaf, including repeated/adjacent special characters (`"**"` → two sentinels, `"Sil*va"` → mid-string sentinel), and correctly leaves an empty string `""` unchanged (no-op).
- Traced why this is a **structural**, not merely empirical, fix: `_BOLD_RE`/`_ITALIC_RE` (now simplified back to plain `\*\*(.+?)\*\*` / `_(.+?)_`, no lookbehind hack) only ever see bare ASCII `*`/`_` characters that survived from **admin-authored** template text — every occurrence originating from a Jinja2-merged leaf has already been replaced with a sentinel before `Template.render()` runs, so there is no longer any bare special character from merged data left in the rendered text for these regexes to pair with, by construction. This holds regardless of how many merge fields appear in one block, how many special characters one leaf contains, or their position (start/middle/end of the leaf) — confirmed by reasoning through the `str.replace` semantics (global, not first-occurrence-only) rather than only trusting the two originally-reported repro cases.
- Block-level classifiers (`_HEADING_RE`, `_UNORDERED_ITEM_RE`, `_ORDERED_ITEM_RE`) run in `_block_flowables` **before** `_inline()`/sentinel-restore, directly against the Jinja2-rendered (but still sentinel-encoded) lines — confirmed this means a merged field starting with `#`/`-`/`*` cannot be misread as a heading/list marker, since by that point it's already a PUA code point, not the ASCII character the classifier regexes require. ### Residual, non-blocking observations (not re-flagged as blocking, new to this pass)

- **Sentinel/real-data collision is theoretical, not reachable in this codebase today.** If a student/plan free-text DB field ever contained a literal Private-Use-Area code point (`U+E000`–`U+E003`) itself — not a Markdown-special character, but the literal sentinel value — `_inline`'s final restore loop would incorrectly convert it into `*`/`_`/`#`/`-` in the rendered PDF, since the restore is a blind `str.replace(sentinel, literal)` over the whole text run, not scoped to only the substitutions `escape_context` itself performed. Was true of the original (pre-Finding-1-fix) design too and was not flagged by the original review; not a regression from this fix pass; noted for completeness only.
