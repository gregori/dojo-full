| 1 | **BLOCKING** | **"Today" and "day-of-week" are used throughout RES-02/RES-04/RES-05/RES-06 without ever stating which calendar-day/timezone frame is authoritative, and this codebase has no existing convention to silently inherit (see ground-truth note above).** Concretely, RES-04's resolution algorithm needs to answer "is today's weekday one of the series' `days_of_week`?" and "does an `Event` row already exist for `(series_id, today)`?" — both require picking a definition of "today" — and RES-02's pre-generation window ("the next 28 days from today") has the identical dependency. | 2 | **BLOCKING** | **RES-04's idempotent-resolution guarantee ("this resolution must be idempotent... never creating two [`Event` rows]") is stated as an absolute requirement, but the described algorithm is a sequential check-then-create with no requirement that it hold under concurrent requests, and the single most likely real-world trigger for this exact code path is several students scanning the same wall-mounted QR within the same second at the start of class.** RES-02 describes generation's idempotency the same way ("generation always checks for an existing `(event_series_id, calendar date)` row first and skips it if found") — again, application-level check-then-create prose, not a requirement that this be race-safe. As written, an implementer following the document literally could build exactly this: `SELECT` for an existing row, then `INSERT` if none found — which is a textbook TOCTOU race under concurrent requests, and would produce two `Event` rows for the same `(series_id, today)` when two scans arrive close enough together (a realistic scenario for a class start, not a contrived adversarial one — directly comparable in plausibility to the Reports PR-5 HIGH finding's "ordinary business data" bar). This would silently violate RES-04's own stated guarantee, split attendance for the same class session across two `Event` rows, and defeat the entire point of "scanning the series QR twice in one day resolves to the same `Event`." The document explicitly and correctly defers *concrete schema shape* to `tech-analyst` ("Concrete data-model shape... migration strategy... is a technical design decision left to tech-analyst"), and this finding does not ask to reopen that — but the *behavioral requirement* that the idempotency guarantee must hold under concurrent access (not just sequential calls) is a product-level correctness requirement, and stating it explicitly is what turns "never creating two" from an aspiration into something a test plan can actually target (a test that only calls the resolution endpoint once at a time would never catch this bug, even though it's the exact bug the guarantee exists to prevent). **Fix guidance:** add one sentence to RES-02 and/or RES-04 stating that the idempotency guarantee must hold under concurrent scans/generation-triggers — e.g., "this guarantee must be enforced in a way that is safe against concurrent requests (e.g., a database-level uniqueness constraint on `(event_series_id, occurrence_date)`, not solely an application-level check-then-create), since concurrent scans of the same wall-mounted QR at class start are an expected, not edge-case, usage pattern" — and add one acceptance-criterion-level test expectation: two near-simultaneous scans/generation-triggers for the same series+date must never result in more than one non-`cancelled`-conflicting `Event` row for that date. This does not dictate the specific schema mechanism (still `tech-analyst`'s call) — only that concurrency-safety is a required property, not an optional implementation nicety. |

## Findings

### Amendment 1 (RES-02 window 28→~365 days) — sound, one minor testability nit

- The reasoning is precise and independently verified (see ground-truth re-verification above): `pre_checkin_service.py` genuinely has no virtual-occurrence fallback, so a short rolling window is a genuine operational fragility. - **Minor, non-blocking:** the window is stated as "~365" (approximate) everywhere it appears (RES-02, RES-05, RES-08, Non-Goals, Constraints) and is never pinned to one exact integer anywhere in the document. The original (pre-amendment) default was stated precisely ("28 days (4 weeks)"). An approximate default is fine as a product decision, but it leaves a literal testability gap: an automated test asserting "the default window generates exactly N rows" has no authoritative N to assert against, and two implementers could reasonably pick 365 vs. 366 (leap year) without contradicting the document. **Recommend:** `tech-analyst` (or a one-line follow-up in `requirements.md`) pin one exact integer (e.g., "365 calendar days, inclusive of today, regardless of leap years") so the acceptance criterion is literally testable, not just directionally testable.

### Amendment 2 (RES-05 reversal, Case A/B/combined rule) — scrutinized hardest, mostly unambiguous, two real gaps found

Walked through the combined rule occurrence-by-occurrence as instructed:

- **Day-of-week + active-date-range condition is complete and correct**, including the `series_end_date`-shortened case: the combined rule's condition is "day-of-week still in the (possibly updated) pattern **and** within the (possibly updated) active date range," and the text explicitly calls out that this "also now covers a shortened `series_end_date` pushing an occurrence out of range, for the same reason." Confirmed explicitly stated, not left to be inferred — matches what the task asked to verify. The same general condition (a symmetric range check) also correctly covers a `series_start_date` moved *later* past an already-generated occurrence's date, even though the document only illustrates the `series_end_date`-shortened example — this is not a gap, since the stated condition ("within the active date range") is already symmetric and doesn't need a second illustrative example to be complete.
- **`start_time` recompute for days that remain is explicit, not vague:** Case A's text explicitly says "if `start_time` changed, the occurrence's `start_datetime` is recomputed using the occurrence's own existing `occurrence_date` combined with the series' new `start_time` (and `end_datetime` recomputed the same way if `duration_minutes` changed)" — this forecloses the vague "fields update in place" reading the task flagged as a risk. Good.
- **`UNIQUE(event_series_id, occurrence_date)` interaction is fine:** confirmed via direct plan.md re-check (above) — RES-05 never proposes changing `occurrence_date`, only fields orthogonal to the unique key. No implied violation.
- **GAP — "kept consistent" is genuinely ambiguous for a re-added day-of-week.** The combined rule's parenthetical — "an already-cancelled future occurrence is not resurrected by this rule, only kept consistent or re-cancelled as the rule below dictates" — correctly answers the resurrection-avoidance question the task asked me to check (confirmed: a cancelled occurrence's `status` is never flipped back to `scheduled` by this rule, even if its day-of-week is later re-added to the pattern and the general condition would otherwise route it to the Case-A "update" branch). However, the phrase "kept consistent" itself is underspecified: does it mean the row's other snapshotted fields (`title`/`location`/`start_datetime`/etc.) *do* get updated on an already-cancelled row (harmless housekeeping, matching Case A's field-sync exactly), or does it mean the row is skipped entirely (untouched) once already cancelled? Both readings are consistent with "not resurrected," but they produce different `Event` rows in the database (a cancelled-with-stale-fields row vs. a cancelled-with-synced-fields row), and only one reading is intended. **Recommend:** one clarifying sentence — e.g., "an already-cancelled occurrence whose day-of-week condition now evaluates true still has its non-status fields synced by Case A's update (for consistency, in case it is ever manually reopened), but its `status` itself is never changed back to `scheduled` by this rule" (or the opposite, whichever the user actually intends) — non-blocking, but genuinely two different implementations are defensible from the current text.
- **GAP (related, more substantive) — no stated recovery path for a day-of-week that is removed and later re-added, given the ~365-day window.** Walking through the actual mechanics: with RES-02's window now generating essentially every not-yet-occurred date up to ~365 days out, when a day is removed (Case B cancels all its not-yet-occurred, already-generated occurrences within that window) and then later re-added, (a) RES-05's own rule explicitly does not resurrect those cancelled rows (confirmed above), and (b) RES-02's idempotent generation explicitly states re-triggering "Generate occurrences" "never creates a duplicate `Event` for a date that already has one for that series, regardless of that row's status (including `cancelled`)" — meaning re-running generation will *also* not create fresh rows for those already-covered dates. The only two ways those dates recover are (i) an admin manually re-opens each individual cancelled `Event` via the existing single-event edit flow (a workaround this document's *pre-amendment* text used to state explicitly for the old, now-reversed D2, but which is not restated anywhere in the current amended text for this specific scenario), or (ii) simply waiting — the rolling window naturally exposes fresh, not-yet-generated dates for that day-of-week only once enough calendar time passes for new dates to enter the ~365-day horizon beyond what a prior generation trigger already covered. Neither path is stated in the document; a reader has to derive both by combining RES-02 and RES-05's text, as this review just did. This is a real, narrow (day removed-then-re-added is a rare edit sequence) but genuine gap in an otherwise very thorough amendment. **Recommend:** one sentence in RES-05 or its Non-Goals cross-reference naming the expected recovery path (most likely: "an admin who wants to reinstate a removed day-of-week's already-cancelled occurrences must do so manually via the existing single-event edit flow, occurrence by occurrence; this rule does not bulk-recover them"), so it's a stated, deliberate scope boundary rather than an implicit consequence nobody decided on purpose.

Neither gap contradicts anything already written, and both are answerable with one sentence each — they read as omissions in an otherwise unusually rigorous amendment, not as ambiguity that would produce inconsistent implementations of the *primary* Case A/Case B behavior itself (which is unambiguous, as confirmed above).
