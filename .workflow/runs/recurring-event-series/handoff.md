## Key Decisions

- Core technical direction (Option A: series-level QR token, resolved to "today's occurrence" at scan time, `Attendance` model/constraint unchanged) was already locked in by the user before this run — not re-litigated.
- **Occurrence generation (open question 1):** both mechanisms, not one — explicit admin-triggered pre-generation (default 28-day/4-week rolling window, idempotent) as the primary path, lazy-create-on-scan as a fallback safety net. Mirrors the Epic 2 Mensalidade "no cron, explicit trigger" precedent.
- **Schedule shape (open question 2):** weekly only, one day-of-week multi-select + one shared `start_time` + optional `duration_minutes` per series. Bi-weekly/monthly patterns and per-day-different-times are explicit non-goals.
- **Series fields (open question 3):** one `event_type_id`/`location`/`minimum_belt_id` per series, confirmed; each generated `Event` snapshots these fields at generation time (plain columns, not a live FK back to the series) — editing a series never retroactively changes an already-generated occurrence.
- **Editing a series (open question 4, flagged D2):** affects only occurrences generated after the edit; already-generated occurrences (past or future) are never bulk-regenerated. Manual per-occurrence correction via the existing single-event edit/cancel flow is the accepted workaround. No bulk-propagate tool built.
- **Deactivating a series (open question 5, flagged D1):** auto-cancels its not-yet-occurred, already-generated `Event` rows; past occurrences are untouched regardless of recorded attendance.
- **Series token (open question 6):** `EventSeries` gets its own persistent `check_in_token`, additive to (not replacing) each generated `Event`'s own independent token — an admin can still print/use an individual occurrence's own QR via the existing, unmodified per-event endpoint.
- **Resolution edge cases (open question 7):** idempotent same-day resolution (keyed on `(series_id, today's date)`, existing row wins over creating a new one, regardless of its status — this deliberately prevents lazy-creation from resurrecting a row an admin explicitly cancelled, e.g. for a holiday); scanning on a non-configured weekday is rejected with a clear error rather than creating an off-schedule occurrence; a `cancelled` resolved occurrence is rejected by the existing, unmodified cancelled-event check-in guard.
- **Backward compatibility (open question 8):** purely additive — one new nullable `event_series_id` FK on `Event`, no existing endpoint/schema/frontend behavior changes for non-series events.
- **Frontend scope (open question 9):** series create/edit form, "Generate occurrences" action, series QR view/print (reusing the existing per-event QR component), `EventsPage.tsx`'s one-off flow left untouched.
- Three defaults (D1, D2, D3 — deactivation auto-cancel behavior, edit-only-affects-future-generation, fixed 28-day default generation window) are written as recommended defaults, explicitly flagged for user sign-off before build per the task's own guidance, but not treated as blocking `tech-analyst`'s design work — mirrors how Epic 2 Phase 3 carried its own D1/D3/D10/D11 gate items forward without blocking scoping.

Full design written to `.workflow/runs/recurring-event-series/plan.md` (Requirements review / Autocrítica / Intended design / Test plan / File-level task breakdown / Risk assessment, house style per `contract-markdown-rendering/plan.md`). **Key decisions:**

- **Timezone mechanism (scrutinized hardest per task instruction):** new `app/core/timezone.py` with a single `APP_TIMEZONE = ZoneInfo("America/Sao_Paulo")` constant and `local_now()`/`local_today()` helpers (stdlib `zoneinfo`, no new dependency). Autocrítica finding: the `America/Sao_Paulo` conversion is only load-bearing where a *calendar date/day-of-week* is derived from "now" (generation window, day-of-week matching, same-day lookup) — instant comparisons (RES-05/RES-06 past/future) are timezone-invariant by construction and don't need special handling, though the design uses the same shared `local_now()` there too for consistency, not because it changes the result.
- **Concurrency-safe idempotency (scrutinized hardest per task instruction):** `Event` gains nullable `event_series_id` FK + nullable `occurrence_date` (Date, snapshotted once, decoupled from any later `start_datetime` edit) and a plain `UNIQUE(event_series_id, occurrence_date)` constraint — confirmed sufficient (no partial/filtered index needed) because both MySQL (prod, confirmed via `docker-compose.yml`, MySQL 8.4) and SQLite (test suite, confirmed via `conftest.py`) treat NULL as distinct for uniqueness, so one-off events (`event_series_id = NULL`) never collide. A single `EventSeriesService._get_or_create_occurrence` choke point (mirroring `mensalidade_service.py`'s exact check-then-insert-then-catch-`IntegrityError`-and-refetch idiom, generalized to return the existing row on conflict rather than just skipping) backs both the pre-generation path (RES-02) and the lazy-create/scan-time resolution path (RES-04) — literally the same code, not just the same guarantee in prose.
- **`days_of_week` storage:** comma-separated string of Monday=0..Sunday=6 integers (Python's `date.weekday()` convention) — not a join table (unjustified for a bounded ≤7-value set), not `class_days`'s unstructured-text precedent (needs to be actually parseable). Frontend never computes a JS weekday index at runtime (`Date.getDay()` is Sunday=0, a real mismatch risk) — sidestepped by a static, hardcoded, Monday-first label array whose index is what's sent to the API.
- **API integration point:** `AttendanceService.check_in_qr` gains exactly one new fallback branch (`Event` token lookup fails -> try `EventSeries` token -> `resolve_today_occurrence`) — not a new endpoint, per RES-04's own explicit wording. No changes to `CheckInQRRequest`, `CheckInPage.tsx`, or `api.ts`.
- **New `EventSeries` CRUD + `POST /event-series/{id}/generate` + `GET /event-series/{id}/qr-code`** in a new `app/api/event_series.py`, mirroring `events.py`/`mensalidades.py`'s existing conventions (instructor/admin auth, `DELETE` = soft "end series" action mirroring `cancel_event`'s soft-cancel idiom).
- **Frontend:** new standalone `EventSeriesPage.tsx` + route + nav entry (not a tab inside `EventsPage.tsx`, to guarantee zero risk to the "completely untouched" one-off flow RES-08 requires) — QR action reuses the corrected ground-truth pattern (plain anchor link, not a fabricated component).

## Requirements Fix Pass (2026-07-27) — post-plan.md amendment, three substantive changes

A live discussion with the user, held *after* `tech-analyst` had already completed and self-reviewed `plan.md` (design complete 2026-07-27), surfaced three product-level decisions that change already-approved requirements — not wording tweaks. `.workflow/runs/recurring-event-series/requirements.md` was amended in place to reflect them; `plan.md` and all source code were deliberately left untouched (`tech-analyst` will redesign the affected parts after this amendment clears review). Mirrors this project's `contract-markdown-rendering/handoff.md` "Requirements Fix Pass" style.

1. **Amendment 1 — generation window default changes from 28 days to ~365 days (RES-02).** Why: a recurring class's schedule effectively only changes at long intervals (semester boundaries), and the existing, separate pre-checkin feature (`pre_checkin_service.py`) strictly requires an already-materialized `Event` row — confirmed via direct code read that `PreCheckIn.event_id` is a required non-nullable FK, `get_public_events` only lists materialized rows beyond a 1-hour cutoff, and `confirm`/`cancel` 404 on any unresolvable `event_id`. A short rolling window meant pre-checkin would silently stop working for a series once generation wasn't re-triggered — an operational fragility the user wants eliminated by construction, not mitigated with reminders. This is a config-value change to the existing, already-designed generation mechanism (the optional per-request window override is unchanged) — no new architecture needed for the default-value change itself. Flagged (not resolved) for `tech-analyst`: generating ~365 rows per request via the existing per-row-commit loop (mirroring `mensalidade_service.py`'s precedent, sized for ~28 rows today) may need a batching/commit-granularity reconsideration at this larger scale.
2. **Amendment 2 — editing a series now propagates to not-yet-occurred generated occurrences, REVERSING the original D2 (RES-05, rewritten).** The user explicitly reversed "edits only affect future generation." New rule, now a decided acceptance criterion, not a sign-off item: Case A (schedule-preserving edits — title, location, event_type_id, minimum_belt_id, start_time, duration) propagates in place to every not-yet-occurred generated `Event` regardless of when it was generated (recomputing `start_datetime`/`end_datetime` from the occurrence's own `occurrence_date` + the series' new `start_time`/`duration_minutes`); Case B (a day removed from `days_of_week`) cancels not-yet-occurred occurrences on that now-removed day instead of leaving them stale, per the user's own framing ("this almost always means that slot is being cancelled, not moved"). Combined rule stated concretely in `requirements.md`: for every not-yet-occurred occurrence, if its day-of-week is still in the (possibly updated) pattern and within the (possibly updated) active date range, update fields in place; otherwise cancel it. Already-occurred (past) occurrences, including ones with recorded attendance, remain untouched — that part of the original principle is unchanged.
3. **Amendment 3 — new RES-09: cancelling any `Event` cascades to cancel its confirmed `PreCheckIn` rows, centrally, closing a pre-existing gap.** User confirmed wanting cancellation to always cascade ("se um treino foi cancelado, pré-checkin também será cancelado"). Investigation confirmed this does **not** happen today for the existing single-event cancel route: `EventService.delete_event` (`event_service.py:110-117`) only sets `status="cancelled"` and never touches `PreCheckIn` — a distinct, unfixed gap from the one place this already works today (`update_event`'s reschedule-into-cutoff-window cascade, `event_service.py:98-103`). The user explicitly agreed to fix this centrally (in `EventService` or wherever cancellation is centrally handled) so the pre-existing single-event path and the two new series-driven paths (RES-05 Case B, RES-06's deactivation cascade) share one behavior instead of duplicating "also cancel PreCheckIn" logic inside the new series service. Explicitly flagged in `requirements.md` as "fixes a pre-existing gap in `EventService.delete_event`, confirmed with the user as in-scope" so it doesn't read as undiscussed scope creep to a future reviewer.

**Consequential documentation updates made in the same pass:**
- RES-03 gained a cross-reference noting the snapshot is no longer permanently frozen for not-yet-occurred occurrences — it's now kept in sync only as an explicit, non-implicit side effect of RES-05's cascade.
- RES-06 (D1) now explicitly states its auto-cancel cascade also cancels confirmed `PreCheckIn` rows (RES-09), applying the new cascade uniformly.
- The "Bulk-editing/regenerating" Non-Goal was replaced with a narrower one (no *separate* bulk-regenerate tool needed, since propagation is now automatic and built into the series-edit action itself).
- "Decisions Requiring Sign-Off" (D1-D3) is rewritten as a resolved-decisions historical record: D1 accepted as originally proposed (plus the new PreCheckIn-cascade extension), D2 reversed, D3's default value changed — none remain open sign-off gates.
- Constraints/testing-mandate section extended to name the new required test coverage (RES-05's Case A/B/combined-rule propagation, RES-09's cascade across all three cancellation paths) and to carry forward Amendment 1's batching flag for `tech-analyst`.

No source code or `plan.md` touched in this pass — `tech-analyst` will redesign the affected parts (data-model/service changes for RES-05's propagation, the centralized PreCheckIn-cancellation hook for RES-09, and the window-default/batching reconsideration for RES-02) once this amendment clears `requirements-reviewer`. Given the reversal of an already-approved decision (D2) and the addition of a cross-cutting bug-fix criterion (RES-09) touching a shared, centralized code path, this warrants a real re-review pass, not a skip-ahead.

## Tech Analyst — Redesign Against Amended Requirements (2026-07-27)

Updated `.workflow/runs/recurring-event-series/plan.md` **in place** (edited the specific affected sections; everything the amendments don't touch — the `EventSeries` model, `app/core/timezone.py`, the `UNIQUE(event_series_id, occurrence_date)` constraint, the `check_in_qr` integration, the API route list, the migration plan's overall shape — is unchanged from the first design pass). Both non-blocking follow-ups from the Amendment Review are resolved directly in this redesign, not deferred to a `product-manager` pass.

**RES-02 (window default 28→365, batching):**
- `DEFAULT_GENERATION_WINDOW_DAYS` pinned to the exact integer **365** (not "~365") — `window_end = today + 364 days`, 365 candidate dates, not leap-year-adjusted, resolving the Amendment Review's testability nit.
- Batching/commit-granularity flag resolved: **kept per-row `db.add()`/`db.commit()`/`IntegrityError`-catch granularity, no batching introduced.** Reasoning documented in plan.md: worst case is still only ~365 simple single-row inserts (bounded by window length, not `days_of_week` count); steady-state re-triggers only insert the new leading-edge dates, not the full window, since existing dates are skipped; this is an explicit human-triggered button click behind the frontend's existing `LoadingSpinner.tsx`, not a hot path; a partial mid-loop failure is a non-issue given idempotency (re-clicking "Generate occurrences" resumes cleanly); batching would add a second commit-boundary/failure-handling concept for a scale that isn't a demonstrated bottleneck (CLAUDE.md "don't overengineer"). Documented as a reasoned estimate, not a benchmark, with batching-every-25-50-rows named as the fallback if real MySQL load testing later shows unacceptable latency.

**RES-05 (edit-propagation reversal) and RES-06 (deactivation), unified:**
- `update_series`'s old "only affects future generation" behavior is fully replaced. New single method, `EventSeriesService._reconcile_future_occurrences`, walks every not-yet-occurred `Event` for the series and applies one predicate, `_matches_schedule(series, occurrence_date)` (a generalization of the old `_is_scheduled_today`, now also reused by `resolve_today_occurrence`): if the occurrence's date still matches the series' current day-of-week/date-range/`is_active` schedule → Case A (sync snapshotted fields in place, recompute `start_datetime`/`end_datetime` from the occurrence's own `occurrence_date` + the series' new `start_time`/`duration_minutes`; if the row was `cancelled`, flip it back to `scheduled` — reactivation); otherwise → Case B (cancel it if not already, cascading to confirmed `PreCheckIn`s via RES-09's new helper).
- This single method absorbs RES-06 entirely — deactivating a series (`is_active=False`) is no longer a separate `_cancel_future_occurrences` path; it's the same reconciliation with `is_active` false forcing every date to mismatch.
- **Resolves both Amendment Review follow-up gaps explicitly:** (a) an already-cancelled occurrence whose date matches the current schedule again has both its fields resynced *and* its status flipped back to `scheduled` (full reactivation, not a "kept consistent but still cancelled" middle state); (b) the recovery path for a removed-then-re-added day-of-week is this exact mechanism — re-adding the day in a subsequent series edit is sufficient, no manual single-event workaround needed.
- **Deliberate, surfaced consequence:** because `is_active` is part of the same match predicate, re-activating a whole series (`is_active` False→True) now also resyncs/reactivates its previously deactivation-cancelled future occurrences — a real behavior change from the original (pre-amendment) plan's test-plan note ("re-activating does not un-cancel anything"), corrected in the Test plan and flagged explicitly in Risk assessment as intended, not a regression.
- Confirmed compatible with generation: `_get_or_create_occurrence`'s existing-row check has no status filter, so a reactivated `scheduled` row is already treated correctly by a later `generate_occurrences` pass with zero code changes to that method.
- **Explicitly NOT reactivated by this rule:** a reactivated occurrence's already-cancelled `PreCheckIn` rows stay cancelled — reactivating the class slot doesn't restore a student's prior confirmed intent; they must re-confirm. Stated explicitly in Risk assessment so this isn't later "fixed" as an oversight.

**RES-09 (new cross-cutting PreCheckIn cascade):**
- New `EventService.cancel_pre_checkins_for_event(db, event)` static method in `app/services/event_service.py` (existing file, confirmed real change, previously absent from the file-level task breakdown) — extracted verbatim from `update_event`'s existing inline reschedule-cutoff cascade (behavior-preserving refactor). `delete_event` now calls it too — the actual bug fix (previously `delete_event` only set `status="cancelled"`, never touching `PreCheckIn`, confirmed by direct code read). `EventSeriesService._reconcile_future_occurrences`'s Case B branch calls the same helper.
- **Placement reasoning (checked for circular imports, not assumed safe):** the helper lives in `event_service.py`, not `pre_checkin_service.py`, because `pre_checkin_service.py` already imports `EventService` from `event_service.py` — placing it in `PreCheckInService` instead would force `event_service.py` to import back, a genuine new import cycle. `event_series_service.py` importing `EventService` from `event_service.py` introduces no cycle (`event_service.py` imports neither `event_series_service.py` nor `pre_checkin_service.py`). A new standalone module was also considered and rejected as unjustified indirection for a four-line function with one real implementation.

**Test plan, File-level task breakdown, Risk assessment** all updated in `plan.md` to match: new/replaced RES-05 reconciliation test cases (Case A field-recompute, Case B cascade, re-added-day-of-week reactivation, whole-series reactivate, reconciliation-idempotency), a new RES-02 365-row commit-strategy test, new RES-09 cascade tests across all three trigger paths including `delete_event`'s fix and `update_event`'s regression-guard; `app/services/event_service.py` and `tests/unit/test_event_service.py` added as modified files (both newly listed, not in the original breakdown); Risk assessment gained four new entries (reactivation-doesn't-restore-PreCheckIns, reactivation-via-whole-series consequence, larger row counts touched per generation/edit at 365-day scale, D1-D3 now historical/resolved not open gates).
