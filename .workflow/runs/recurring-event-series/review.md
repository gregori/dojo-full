## Findings (all non-blocking; ranked by severity)

### 1. [LOW — correctness/validation gap] `EventSeriesCreate.validate_dates` doesn't catch `series_end_date` before the *effective* (defaulted) `series_start_date`

`app/schemas/event_series.py`'s `validate_dates` only fires `if self.series_end_date and self.series_start_date and ...` — but `series_start_date` defaults to `local_today()` **later, in the service layer** (`create_series`: `series_start_date=data.series_start_date or local_today()`), not in the schema. If a client omits `series_start_date` and supplies a `series_end_date` that is in the past (e.g. a copy-paste mistake), the schema validator sees `self.series_start_date is None` and skips the check entirely, silently letting `create_series` construct a series whose effective `series_end_date < series_start_date`. Functionally this doesn't crash — `generate_occurrences`'s `window_start <= window_end` guard correctly makes it a permanent no-op — but it's a silently broken series with no error surfaced to the admin who created it, and no test covers this specific omitted-start-date combination (`test_series_end_date_before_start_date_rejected` only supplies both dates explicitly). **Fix suggestion:** validate against `self.series_start_date or date.today()` (or move the check into `create_series` after the default is applied).

### 2. [LOW — correctness/validation gap] `duration_minutes` has no positivity constraint, unlike the existing `EventCreate` precedent

`EventSeriesBase.duration_minutes: int | None = None` has no `gt=0`/similar constraint, and neither `EventSeriesCreate` nor `EventSeriesUpdate` has a model validator for it. The existing, directly-analogous `EventCreate` schema (`app/schemas/event.py:40-43`) explicitly validates `end_datetime > start_datetime`. A negative or zero `duration_minutes` on a series would silently produce `end_datetime <= start_datetime` for every generated occurrence (`_get_or_create_occurrence`/`_reconcile_future_occurrences` both compute `end_datetime = start_datetime + timedelta(minutes=series.duration_minutes)` unconditionally). Not tested; not currently reachable from the frontend form (a `min={1}` on the number input), but reachable directly via the API. **Fix suggestion:** add `gt=0` to `duration_minutes` (e.g. `Annotated[int, Field(gt=0)] | None`).

### 3. [LOW — maintainability/DRY] `generate_occurrences`'s window loop duplicates `_matches_schedule`'s predicate instead of reusing it

`plan.md`'s own Autocrítica states the point of generalizing `_matches_schedule` was "one place computes 'does this date match this series' current schedule,' not two" — but `generate_occurrences` re-implements the day-of-week/date-range/`is_active` check inline (`current.weekday() in days_of_week`, an outer `series.is_active` gate, and window clamping that separately encodes the `series_start_date`/`series_end_date` bounds) rather than calling `_matches_schedule(series, current)`. Verified the two implementations are logically equivalent today at every boundary (confirmed no live bug), but this is exactly the kind of latent drift risk the plan said it wanted to avoid — a future edit to one predicate without the other would silently desync generation from resolution/reconciliation. **Fix suggestion:** have the loop call `_matches_schedule(series, current)` (or at least the day-of-week check) instead of re-deriving it.

### 4. [LOW — data hygiene, not an acceptance-criteria violation] `_reconcile_future_occurrences` stamps `event.updated_at` with a São-Paulo-based instant, inconsistent with every other timestamp write in the codebase

`_reconcile_future_occurrences` sets `event.updated_at = now` where `now = local_now()` (tzinfo=`APP_TIMEZONE`). Every other `updated_at`/`created_at` write in this codebase — including `update_series`'s own `series.updated_at = datetime.now(UTC)` a few lines earlier in the *same file* — uses `datetime.now(UTC)`. Because this codebase's `DateTime(timezone=True)` columns round-trip **without** tzinfo (a pre-existing, documented quirk — see `tests/unit/test_medical_exam_service.py:59`'s own comment, "SQLite round-trips DateTime(timezone=True) columns without tzinfo"), the raw wall-clock digits actually persisted for a reconciled `Event.updated_at` will be São-Paulo-local (3 hours behind UTC), while that same row's own `created_at` (via `TimestampMixin`'s UTC-based default) and every other table's timestamps are UTC-based. This doesn't violate any RES-0X acceptance criterion (`plan.md`'s own Autocrítica correctly notes instant *comparisons* are unaffected), but it is a real, avoidable inconsistency in stored data that could confuse a future maintainer inspecting raw `updated_at` values. **Fix suggestion:** use `datetime.now(UTC)` for `event.updated_at` here, matching `event_service.py`'s convention (this is exactly the kind of instant-only bookkeeping field the plan's own Autocrítica said doesn't need the `America/Sao_Paulo` conversion).

### 5. [Informational, not a new bug] `GET /event-series/{id}` and `GET /event-series/{id}/qr-code` don't explicitly 404 on a nonexistent `series_id`

Both routes return/dereference `EventSeriesService.get_series(...)` without a `None` check, which would surface as a FastAPI response-validation error (for `get_series`) or an unhandled `AttributeError` (for `get_series_qr_code`, `series.check_in_token` on `None`) rather than a clean 404. Confirmed this is a **faithful, deliberate mirror** of the exact same pre-existing pattern in `app/api/events.py`'s `get_event`/`get_event_qr_code` (both have the identical gap, side by side, confirmed by direct comparison) — not a regression or something new this feature introduces. Consistent with the plan's explicit "mirrors `events.py`'s conventions exactly." Worth a future cleanup pass across both files together, not blocking this feature.

### 6. [Informational] Simulated-race tests share one physical SQLite connection under `StaticPool`

Both concurrency tests bind their "competitor" `Session` to the same `db_engine` fixture, which uses `StaticPool` — the mechanism SQLite `:memory:` testing relies on to keep a single, shared physical connection alive across multiple `Session`/`Engine` checkouts. This means the two "independent" sessions are not as isolated as two genuinely separate MySQL connections would be in production. Traced the actual sequencing anyway (see Ground-truth section above) and confirmed the tests still force the intended check → competitor-commits → own-commit-fails interleaving and genuinely exercise the `IntegrityError` catch-and-refetch path — not a defect, and exactly the test methodology the requirements/plan text explicitly sanctioned ("real thread-level concurrency not required"). Noted for context only.
