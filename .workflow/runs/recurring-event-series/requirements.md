## Context

A dojo runs recurring weekly classes — e.g. "Aikido geral" every Monday/Wednesday/Saturday morning, plus other sessions on different evenings. Today, ground-truth confirmed directly against the codebase:

- `Event` (`dojo-app/backend/app/models/__init__.py`, ~174-200) represents exactly one dated occurrence: `title`, `event_type_id`, `description`, `start_datetime`/`end_datetime` (both single `DateTime`), `location`, `created_by`, `organization_id`, a unique `check_in_token` used to generate a QR code for check-in, `status` (`scheduled`/`in_progress`/`finished`/`cancelled`), `minimum_belt_id`.
- `EventType` (~121-132) is only a category label (`name`, `color`, `counts_for_belt`) — not a schedule.
- There is no recurrence concept anywhere in the codebase (no `day_of_week`/`rrule`/`repeat`/`series` field on any model, service, API, or frontend form). `EventsPage.tsx`'s form creates one `Event` row at a time via `POST /api/v1/events` → `EventService.create_event`.
- `Attendance` (~203-220) has a unique constraint on `(event_id, student_id)` and always requires a concrete `event_id`. `AttendanceService.check_in`/`check_in_qr`/`create_manual_attendance` always resolve a specific `Event` row (via `EventService.get_event`/`get_event_by_token`) before recording attendance. `check_in`/`check_in_qr` already reject a `status == "cancelled"` event with a 400 (`attendance_service.py` lines 51-52, 98-99) — this existing guard is relied on below, not re-implemented.
- `GET /events/{event_id}/qr-code` (`app/api/events.py` ~105-111) returns `{"check_in_token": event.check_in_token, "url": f"/checkin?token={event.check_in_token}"}`; the frontend `/checkin` page (`CheckInPage.tsx`) posts that token to `POST /checkin/qr`.
- **Ground truth added in the 2026-07-27 amendment pass, confirmed via direct code read:** `pre_checkin_service.py`'s `PreCheckIn.event_id` is a required, non-nullable FK — there is no lazy/virtual-occurrence support anywhere in pre-checkin's public surface. `get_public_events` only lists already-materialized `Event` rows whose `start_datetime` is beyond a 1-hour cutoff; `confirm`/`cancel` 404 on any `event_id` not resolvable via `EventService.get_event`. A series with only a short rolling generation window silently stops offering pre-checkin once the window runs out, unless an admin remembers to keep re-triggering generation.
- **Also confirmed in the 2026-07-27 amendment pass:** `EventService.delete_event` (`event_service.py:110-117`, the handler behind the existing `DELETE /events/{event_id}` cancel route) only sets `event.status = "cancelled"` — it never touches `PreCheckIn` rows. The only place `PreCheckIn` gets auto-cancelled today is inside `update_event`'s reschedule-into-cutoff-window logic (`event_service.py:98-103`), which sets `status="cancelled"` and `cancelled_at` on `confirmed` `PreCheckIn` rows for that event. Cancellation via the `DELETE` route is a distinct, unfixed code path with the same class of gap — a pre-existing bug, not something this feature introduces.

**The problem:** because a QR code is tied to one `Event`'s `check_in_token`, printing a QR for a wall-mounted, scan-to-check-in class requires a new QR for every single calendar date — defeating the point of a physical, printed code for a recurring class.

## Decision already locked in (do not re-litigate)

The user chose **Option A**: introduce a real recurring-series concept. A QR code belongs to the *series*, not to one calendar occurrence. At scan time, the system resolves the series' token to "today's occurrence" — either an already-generated `Event` row for today, or one created on the fly following this codebase's existing no-cron, explicit-trigger idiom (`.workflow/epic-02/handoff.md`: "no scheduler infra exists in this codebase, so monthly [mensalidade] generation is an explicit, idempotent instructor/admin-triggered action, not a cron job"). Attendance keeps being recorded against a concrete `Event` row exactly as today — `Attendance`'s model and uniqueness constraint are unchanged; this feature only adds a resolution layer in front of the existing check-in flow. Option B (bulk QR printing, no series concept) was explicitly rejected — it doesn't solve the reprinting problem.

This document resolves the product-level specifics Option A leaves open, per the nine numbered questions the user raised.

## User Persona

**Dojo admin / instructor** — creates and maintains the dojo's class schedule via the existing `EventsPage.tsx` (one-off events, unchanged) and a new series-management surface (recurring classes). Prints and posts a QR code on the wall for students to scan for check-in to a recurring class, without ever needing to reprint it as new calendar dates pass.

## Business Outcome

An admin sets up a weekly recurring class once, prints its QR code once, and students self-check-in against the correct calendar occurrence indefinitely — with no more manual per-date `Event` creation and no reprinting — while every existing one-off event, and the entire existing attendance/check-in data model, keeps working exactly as it does today.

## In Scope

### A new `EventSeries` concept (additive, not a replacement for `Event`)

A series describes a recurring weekly class: which day(s) of the week, at what time, for what duration, of what `EventType`, at what location, with what minimum-belt gate — mirroring the single set of fields an individual `Event` already carries. Occurrences are still ordinary `Event` rows; the series is a template that produces them and a stable, printable QR token that resolves to "today's" one.

### RES-01 — Series schedule definition

An admin can create an `EventSeries` with: `title`, `event_type_id`, `description` (optional), `location` (optional), `minimum_belt_id` (optional) — one value each, shared by every occurrence the series generates (mirrors today's single-`Event` fields, confirming open question 3) — plus:

- **`days_of_week`**: a multi-select of one or more weekdays (e.g. Monday, Wednesday, Saturday). All selected days share the **same** `start_time` and `duration` — a series cannot have a different time per day (see Non-Goals).
- **`start_time`**: a single time-of-day (e.g. 07:00).
- **`duration_minutes`**: optional, mirrors `Event.end_datetime`'s optional nullability — if provided, a generated occurrence's `end_datetime` is computed as `start_datetime + duration_minutes`; if omitted, the generated occurrence has no `end_datetime`, exactly like today's optional-end-time `Event`s.
- **`series_start_date`**: the date the series becomes effective (defaults to the creation date).
- **`series_end_date`**: optional; if omitted, the series recurs "until cancelled" (see RES-06).
- **`is_active`**: boolean, defaults `true`.

Only a simple **weekly** pattern is supported (resolves open question 2). Bi-weekly, monthly, or any non-weekly recurrence rule is an explicit non-goal (see Non-Goals) — the real-world scenario driving this feature ("every Monday/Wednesday/Saturday") is fully satisfied by weekly + a day-of-week multi-select, and anything more expressive is not needed to satisfy it.

### RES-02 — Occurrence generation is pre-generation-first, lazy-create as a fallback safety net

Resolves open question 1 by combining the two viable options rather than choosing only one, matching the task's own suggested resolution:

- **Timezone / "today" definition — governs "today," "now," and "day-of-week" everywhere in this document (RES-02, RES-04, RES-05, RES-06).** This codebase has no per-organization/per-dojo timezone concept anywhere today (no timezone field on `Organization` or `Dojo`; every existing "now" comparison in the codebase uses bare `datetime.now(UTC)`), and introducing a configurable, per-organization timezone is explicitly out of scope for this feature (see Non-Goals). For this feature only: **"today," "now," and "day-of-week" are computed against a single, hardcoded, application-wide timezone constant, `America/Sao_Paulo`** — consistent with this app's existing `pt-BR` locale and domain vocabulary ("mensalidade", "presenças"). Concretely, this means the rolling generation window's start date, day-of-week matching, and same-day occurrence lookup/resolution (RES-04) must all be computed from the current wall-clock date/time in `America/Sao_Paulo`, not from the raw UTC calendar date `datetime.now(UTC)` would otherwise yield. This is a required product behavior, stated explicitly so `tech-analyst` has one unambiguous rule to implement against and testers have one unambiguous rule to test against — not a detail left to be invented during implementation.
- **Primary path — explicit, admin-triggered pre-generation.** Mirroring the Mensalidade precedent, an admin/instructor explicitly triggers "Generate occurrences" for a series. This creates one `Event` row for every date, within a rolling window, that falls on one of the series' `days_of_week` and within `[series_start_date, series_end_date or unbounded]`. **Default window (revised by Amendment 1, 2026-07-27 — decided, not a sign-off item): the next ~365 calendar days starting today** (in the `America/Sao_Paulo` sense defined above), inclusive of today — i.e. if today matches one of the series' `days_of_week` and no `Event` row exists yet for `(series_id, today)`, today itself is included as one of the generated dates, not skipped as an already-past boundary. This changes only the *default value*, not the mechanism — the existing design already allows an optional per-request override of the window size; that override capability is unchanged, only the un-overridden default grows from 28 to ~365. Rationale: a recurring class's schedule effectively only changes at long intervals (e.g. semester boundaries), and the existing, separate pre-checkin feature strictly requires a materialized `Event` row to exist (see updated Context) — a short rolling window means pre-checkin silently stops working for a series once generation isn't re-triggered, an operational fragility the user wants eliminated by construction rather than mitigated by reminders or auto-top-up tricks.
  - **Flag for `tech-analyst` (not resolved here, just surfaced):** generating on the order of ~365 rows in a single request via the existing per-row-commit loop (mirroring `mensalidade_service.py`'s precedent, ~28 rows today) is an order-of-magnitude larger batch. Whether the existing per-row-commit granularity still holds up at this scale (performance, partial-failure blast radius, request duration) is worth revisiting during design — this document does not prescribe a fix, only flags it as something to reconsider now that the default window is ~13x larger.
- **Idempotent, including under concurrent requests.** Re-triggering generation (e.g. weekly, to roll the window forward) never creates a duplicate `Event` for a date that already has one for that series, regardless of that row's `status` (including `cancelled` — see RES-04's edge case). This "never a duplicate row for the same `(event_series_id, occurrence_date)`" guarantee must hold even if two generation triggers (or a generation trigger and a lazy-create scan, RES-04) race concurrently — an application-level "check for an existing row, then insert if none found" is not sufficient on its own, since two concurrent requests can both pass the check before either inserts. The required **outcome** is: it must be impossible for two `Event` rows to ever exist for the same `(event_series_id, occurrence_date)` pair, no matter how requests are timed. In practice this means a database-level uniqueness guarantee (e.g. a unique constraint on `(event_series_id, occurrence_date)`) backing the check-then-create logic, with the creating code handling the resulting integrity error on a race by re-fetching the now-existing row — but the precise mechanism is `tech-analyst`'s design call; this document states the required guarantee, not the implementation.
- **Fallback — lazy creation at scan time.** If the series' QR is scanned on a day that is one of its configured `days_of_week`, and no `Event` row exists yet for `(series_id, today)` (e.g. generation was never run, or hasn't caught up yet), exactly one `Event` is created on the fly for today, with the same field-snapshot behavior as pre-generated occurrences (RES-03). This is a safety net, not the primary mechanism — an admin who never runs "Generate occurrences" still gets a working check-in flow, but loses the ability to see/print a roster or pre-checkin ahead of the day.
- Each generated `Event` (pre-generated or lazily created) is otherwise an ordinary `Event` row: it gets its own independently generated `check_in_token` exactly as `EventService.create_event` does today, `status` defaults to `scheduled`, and it is fully usable via every existing event/attendance/pre-checkin code path with no special-casing.

### RES-03 — Field snapshot at generation time, not a live reference

Resolves open question 3's second half. Each generated `Event` occurrence copies `title`, `event_type_id`, `description`, `location`, `minimum_belt_id`, and computed `start_datetime`/`end_datetime` from the series **at the moment it is generated** (pre-generation or lazy-create). These are plain column values on the `Event` row, not a live foreign key back to the series.

**Amended cross-reference (Amendment 2, 2026-07-27):** this snapshot is no longer permanently frozen for not-yet-occurred occurrences — RES-05 (revised) now requires the snapshotted fields of not-yet-occurred generated occurrences to be updated in place, or the occurrence cancelled, as an explicit side effect of a series edit. This remains "snapshot, not live reference" in the sense that matters: there is no read-time join back to the series and no automatic drift — the fields only ever change as a direct, explicit consequence of an admin editing the series (RES-05's cascade), never implicitly. Already-occurred (past) occurrences are never touched by this, with or without recorded attendance — that part of the original principle is unchanged.

### RES-04 — Series-level check-in token and same-day resolution

Resolves open questions 6 and 7.

- `EventSeries` gets its **own** persistent, unique `check_in_token` (independent of any `Event.check_in_token`), generated once at series creation and never rotated by this feature. A new `GET /event-series/{id}/qr-code`-equivalent endpoint returns it in the same shape as today's per-event `qr-code` endpoint (`{"check_in_token": ..., "url": "/checkin?token=..."}`), so the existing `/checkin` frontend page and its QR-encoding logic need no format change.
- Each generated `Event` occurrence **also keeps its own independent `check_in_token`**, unchanged from today's per-event behavior — this is additive, not a replacement. An admin can still fetch and print an individual occurrence's own QR (e.g. a one-time manual override, or a special date printed separately) via the existing `GET /events/{event_id}/qr-code` endpoint, untouched.
- **Resolution at scan time.** The existing check-in-by-QR flow (`POST /checkin/qr` → `AttendanceService.check_in_qr`) is extended, not replaced: given a scanned token, it is first looked up as an `Event.check_in_token` (today's behavior, unchanged); if not found, it is looked up as an `EventSeries.check_in_token`. If the token matches a series, the system resolves "today's occurrence" as follows — "today" here means the `America/Sao_Paulo` wall-clock calendar date defined in RES-02, not the server's raw UTC date — **and this resolution must be idempotent, including under concurrent requests**: scanning the same series token multiple times in the same day, even by several students within the same second (the expected, ordinary way a wall-mounted QR is used at class start, not a rare edge case), resolves to the same single `Event` row every time, and it must be impossible for concurrent scans to ever create two `Event` rows for the same `(series_id, today's date)`. This concurrency-safety requirement is the same guarantee, and the same expected mechanism (a database-level uniqueness constraint backing the check-then-create/fetch-or-create logic, per RES-02), as generation's idempotency — resolution and generation both write through the same guarantee, they are not two separate correctness requirements:
  1. If an `Event` row already exists for `(series_id, today's date)` — **regardless of its `status`**, including `cancelled` — that row is used. This is deliberate: it prevents lazy-creation from silently resurrecting/bypassing an admin's explicit single-occurrence cancellation (e.g. a holiday) with a fresh duplicate `Event`. A `cancelled` occurrence found this way is then rejected by the existing, unmodified `check_in_qr` cancelled-event guard (`attendance_service.py` line 98-99) — no new cancellation-checking logic is needed here.
  2. If no `Event` row exists for that date, and today's weekday **is** one of the series' `days_of_week`, and today falls within `[series_start_date, series_end_date or unbounded]`, and the series `is_active` — the lazy-create fallback (RES-02) creates exactly one `Event` for today, and that row is used.
  3. If no `Event` row exists for that date and today's weekday is **not** one of the series' configured days (or the series is inactive, or today is outside its active date range) — the scan is rejected with a clear 400 error (e.g. "No occurrence scheduled today for this series"). The system never creates an off-schedule occurrence just because a token was scanned.
  4. Once a concrete `Event` is resolved, check-in proceeds exactly through the existing `AttendanceService.check_in` path, with no change to `Attendance`'s model, uniqueness constraint, or any existing validation (student lookup, PIN check, already-checked-in check, cancelled-event check).

### RES-05 — Editing a series propagates to not-yet-occurred generated occurrences

**Revised by Amendment 2 (2026-07-27) — this REPLACES the original RES-05/D2 default entirely.** The user explicitly reversed the original "edits only affect future generation" behavior after commissioning `tech-analyst`'s design. This is now a decided, normal acceptance criterion — not a sign-off item.

- **Case A (common) — editing fields that don't change which dates are scheduled**: `title`, `location`, `event_type_id`, `minimum_belt_id`, `start_time`, `duration_minutes`. Any such edit propagates to **every not-yet-occurred generated `Event` occurrence for that series** — i.e. every `Event` row with `event_series_id` equal to this series and `start_datetime` still ahead of "now" (the same `America/Sao_Paulo`-based "future" definition used throughout this document, per RES-02) — regardless of when those rows were originally generated (including rows generated long before the edit, under RES-02's ~365-day window). Already-occurred (past) occurrences, including ones with recorded attendance, remain completely untouched/frozen — this part of the original principle is unchanged. Concretely: an already-generated future occurrence's snapshotted fields (RES-03) are updated in place to match the series' new values; if `start_time` changed, the occurrence's `start_datetime` is recomputed using the occurrence's own existing `occurrence_date` combined with the series' new `start_time` (and `end_datetime` recomputed the same way if `duration_minutes` changed).
- **Case B (rare) — removing a day from `days_of_week`.** Per the user's own framing: "in practice, this almost always means that specific training slot is being cancelled, not moved to another day." So: when a series edit results in a previously-scheduled day-of-week no longer being in the pattern, any not-yet-occurred generated `Event` occurrence that was on that now-removed day-of-week is **cancelled** (`status="cancelled"`) — not deleted, not left as-is with a stale schedule. Per RES-09, this cancellation also cascades to cancel that occurrence's `confirmed` `PreCheckIn` rows, exactly like any other event cancellation. Occurrences on days-of-week that remain in the pattern are handled by Case A's in-place field update instead (including a `start_time` change for the days that remain).
- **Combined rule (concrete, testable statement):** on any series update, for every not-yet-occurred `Event` occurrence belonging to that series (regardless of its current status other than already-occurred/past — an already-cancelled future occurrence is not resurrected by this rule, only kept consistent or re-cancelled as the rule below dictates): if the occurrence's `occurrence_date`'s day-of-week is still in the series' (possibly updated) `days_of_week` set **and** within the series' (possibly updated) active date range (`[series_start_date, series_end_date or unbounded]`) — update its snapshotted fields to the series' new values (Case A); **otherwise** — cancel it (Case B, which also now covers a shortened `series_end_date` pushing an occurrence out of range, for the same reason: the date is effectively being un-scheduled, not moved).
- There is still no separate, admin-facing "regenerate/backfill" tool needed for this propagation — it is a required, automatic side effect of the series-update action itself (RES-01's create/edit form), not a manual re-trigger step. "Generate occurrences" (RES-02) remains a separate action solely for producing *new* rows within the (now ~365-day) window; RES-05's propagation only ever touches rows that already exist.

### RES-06 — Deactivating/ending a series

Resolves open question 5. Setting `EventSeries.is_active = false` (or an equivalent "end series" action) **auto-cancels every not-yet-occurred, previously-generated `Event` row belonging to that series** — i.e. every generated occurrence whose `start_datetime` is still in the future, "future" measured against the same `America/Sao_Paulo` "today" defined in RES-02, has its `status` set to `cancelled` (the same terminal state produced by the existing single-event cancel action), preventing further check-ins against them via the existing cancelled-event guard **and cascades to cancel their confirmed `PreCheckIn` rows too** (RES-09 — the same PreCheckIn-cancellation behavior applies uniformly across every cancellation path this feature and the existing codebase have, not just this one). Occurrences whose `start_datetime` has already passed are left untouched regardless of attendance recorded against them. Deactivating a series also stops both the pre-generation window and the lazy-create fallback from producing any further occurrences for it. **Decided (2026-07-27), no longer a sign-off item** — the user explicitly confirmed this default (auto-cancel, including the PreCheckIn cascade) over the alternative of leaving abandoned-but-still-`scheduled` future occurrences on the calendar. See "Decisions Requiring Sign-Off" for the resolution record.

### RES-07 — Backward compatibility

Resolves open question 8. Every existing `Event` row (created the old way, no series) and the entire existing one-off event-creation flow (`EventsPage.tsx`'s form → `POST /events` → `EventService.create_event`) continue to work exactly as today, unchanged. A series is purely additive: `Event` gains one new nullable `event_series_id` foreign key (null for every pre-existing row and every newly created one-off event), and no existing endpoint, schema field, or frontend form changes its existing behavior for non-series events.

### RES-08 — Frontend scope

- A "Generate occurrences" action/button on a series (triggers RES-02's primary path with its default ~365-day window, per Amendment 1).

### RES-09 — Cancelling any `Event` cascades to cancel its confirmed PreCheckIn rows (new, Amendment 3, 2026-07-27)

**Fixes a pre-existing gap in `EventService.delete_event`, confirmed with the user as in-scope** — this is a small, explicitly-in-scope bug fix to the *existing* single-event cancellation path, bundled into this feature specifically because centralizing it is what lets the new recurring-series cascades (RES-05 Case B, RES-06) behave correctly without duplicating "also cancel PreCheckIn" logic inside the new `EventSeriesService`. This is not silent, undiscussed scope creep — it is called out explicitly here for that reason.

- **Required behavior:** whenever any `Event`'s `status` transitions to `"cancelled"` — via any of:
  1. the existing single-event cancel route (`DELETE /events/{event_id}` → `EventService.delete_event`, today confirmed to only set `status="cancelled"` and touch nothing else),
  2. the new series-edit cascade's Case B (RES-05, a now-off-schedule day-of-week occurrence), or
  3. the original series-deactivation cascade (RES-06) —

  then all `PreCheckIn` rows for that `Event` with `status="confirmed"` must also transition to `status="cancelled"`, setting `cancelled_at` per the existing `PreCheckIn` model's field — the same target state `update_event`'s existing reschedule-into-cutoff-window cascade already produces (`event_service.py:98-103`), just triggered from a different source event/code path, not a new or different terminal state being invented.
- **Centralization requirement:** this behavior must live in one place (`EventService` or wherever event cancellation is centrally handled), shared by all three paths above, rather than duplicated separately inside `EventSeriesService` for the two series-driven paths. This is what makes the new series cascades "just work" once the existing single-event path is fixed, instead of requiring the same logic to be written twice.
- **Scope boundary:** this only fires on a transition *into* `"cancelled"`. It does not change any other `Event` status transition (`scheduled` → `in_progress` → `finished`), and it does not change `PreCheckIn`'s own existing cancellation reasons/flows (e.g. a student or admin directly cancelling a still-confirmed pre-checkin) — those are untouched.

## Explicit Non-Goals

- **Bi-weekly, monthly, or any non-weekly recurrence pattern.** Only simple weekly recurrence (a day-of-week multi-select) is supported. This is a deliberate scope boundary, not an oversight — the real scenario driving this feature is fully weekly.
- **Different start times per day within one series.** All of a series' selected `days_of_week` share one `start_time`/`duration_minutes`. A dojo wanting Monday-morning and Wednesday-evening sessions under the same `EventType` creates two separate series.
- **A separate, admin-facing "bulk regenerate" tool distinct from RES-05's automatic propagation.** ~~Original non-goal, superseded by Amendment 2~~ — RES-05 (revised, 2026-07-27) now requires automatic in-place propagation/cancellation of not-yet-occurred occurrences as a direct side effect of a series edit, so a *separate* manual bulk-regenerate action is unnecessary and remains out of scope, not because propagation itself is unsupported (it now is, per RES-05) but because the series-edit action itself is the only trigger needed.
- **Any new background job/scheduler infrastructure (cron, Celery beat, etc.).** Both generation paths (explicit pre-generation trigger, lazy-create-on-scan) are triggered by an actual HTTP request from a human action, mirroring the Mensalidade precedent — no code in this feature runs on a timer.
- **Any change to `Attendance`'s model, its `(event_id, student_id)` uniqueness constraint, or the check-in validation chain (student lookup, PIN, already-checked-in, cancelled-event guard).** This feature only adds a token-resolution step in front of the existing, unmodified `check_in_qr` flow.
- **Any change to the existing per-event QR/check-in mechanism.** `GET /events/{event_id}/qr-code` and one-off event check-in via `Event.check_in_token` are untouched — the series token is a strictly additive second way to reach a concrete `Event`, not a replacement.
- **Roster/attendance-preview UI keyed by series** (e.g. "show me all future occurrences of this series at a glance") — a nice-to-have not required by this scope; occurrences remain visible and manageable via the existing `EventsPage.tsx` list like any other `Event`.
- **A per-series persisted/configurable window-size setting.** The existing design's optional per-request override to the generation window (unchanged by Amendment 1 — only the un-overridden *default* changed, from 28 to ~365 days) is not a per-series persisted setting exposed in the UI as a new configuration concept in this scope.
- **Per-organization/per-dojo configurable timezone.** This codebase has no timezone concept on `Organization`/`Dojo` today. This feature does not add one — RES-02's `America/Sao_Paulo` constant is a single, hardcoded, application-wide value used for every "today"/day-of-week computation this feature needs, for every organization in this deployment. Supporting dojos in other timezones (a per-organization or per-dojo timezone field) is a reasonable future enhancement but is explicitly out of scope here.

## Constraints

- No new background job/scheduler infrastructure — both generation paths are explicit, human-triggered HTTP actions (mirrors Epic 2 Phase 3's Mensalidade precedent).
- `Attendance`'s model and uniqueness constraint are unchanged; attendance is still always recorded against one concrete `Event` row.
- The existing per-event check-in token/QR mechanism is unchanged; the series token is additive only.
- A series' generated occurrences are field-snapshotted at generation time, never a live reference back to the series (RES-03) — this is a data-integrity requirement, not an implementation suggestion.
- **Timezone constant (RES-02).** Every "today"/"now"/day-of-week computation this feature performs (generation window, day-of-week matching, same-day resolution) uses the fixed `America/Sao_Paulo` timezone, not the server's raw UTC clock — this is a required product behavior, not left to `tech-analyst` to choose. No per-organization/per-dojo timezone configuration is in scope (see Non-Goals).
- **Concurrency-safe idempotency (RES-02, RES-04).** "Never a duplicate `Event` row for the same `(event_series_id, occurrence_date)`" must hold under concurrent requests, not only sequential ones — the required outcome is stated as a requirement; a database-level uniqueness constraint is the expected mechanism, but the exact design (constraint shape, race-handling code) is left to `tech-analyst`.
- Per `CLAUDE.md`'s repository-wide testing mandate, every RES-0X criterion must be covered by automated tests: backend unit tests (series CRUD, generation idempotency **including a concurrent-requests test that two near-simultaneous generation-triggers/scans for the same series+date never produce more than one `Event` row**, field-snapshot behavior, token resolution including all four RES-04 edge cases, deactivation auto-cancel behavior including the `PreCheckIn` cascade, `America/Sao_Paulo`-based day-of-week/"today" computation, RES-05's amended propagation rule — Case A in-place field update including recomputed `start_datetime`/`end_datetime`, Case B day-removed cancellation including its `PreCheckIn` cascade, and the combined rule's date-range-shortened variant — and RES-09's cascade behavior across all three cancellation paths) and end-to-end coverage (Behave/pytest-BDD for the check-in resolution flow, Cypress for the new frontend series-management surface) — mirroring how Epic 2's phases each got a "### Test plan" subsection in their implementation plan. Exact test file/case breakdown is left to `tech-analyst`.
