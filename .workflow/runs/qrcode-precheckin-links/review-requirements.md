## Findings

| # | Severity | Finding |
|---|---|---|
| 1 | Non-blocking, fold in when convenient | **QRL-10 (responsive modal) is the one criterion of the ten that isn't clearly testable via this repo's Jest/jsdom stack, and the Constraints section's own test-coverage enumeration doesn't mention it.** QRL-10 is stated in concrete, non-vague terms ("remain fully visible and usable without horizontal overflow... without requiring the admin to resize their browser window") — that's good, it's not hand-wavy. But `jsdom` (used by this repo's Jest config) has no real CSS layout engine, so a Jest/RTL component test cannot meaningfully assert "no horizontal overflow" the way it can assert, say, a toast's text content or a clipboard call — that assertion only becomes real in a real browser, i.e. Cypress with `cy.viewport()` at a narrow width plus a `scrollWidth`/`clientWidth` (or visibility) check. The Constraints section is otherwise precise about which layer covers what ("Jest unit/component tests for the QR modal... the print page's content and print-trigger behavior, the copy-link buttons'... clipboard-invocation... and the toast feedback..."; "Cypress end-to-end coverage for the full admin flow: open QR modal..., open the print page..., click both copy-link buttons...") but never assigns QRL-10 to either bullet. As written, an implementer following the Constraints section literally could ship QRL-10 with zero automated coverage and still believe every enumerated test bullet was satisfied — which would violate `CLAUDE.md`'s "every acceptance criterion must be covered by automated tests" mandate for exactly this one criterion. **Fix guidance:** add QRL-10 explicitly to the Cypress bullet in Constraints, e.g. "...and a narrow-viewport (e.g. mobile-width `cy.viewport`) check that the QR modal's title, image, and print control remain visible with no horizontal scroll (QRL-10)." One sentence, no re-scoping. |
| 2 | Non-blocking, optional | **QRL-04's print-page sizing language ("sized so the QR code is legible and scannable at typical wall-posting viewing/scanning distance") has no pinned, assertable value**, unlike the rest of the document's generally concrete style. "Legible at typical viewing distance" is real user intent but isn't literally assertable by an automated test the way "an image element is present with at least a 400px rendered width" would be. This mirrors a pattern seen in this repo's prior review-requirements passes (recurring-event-series' Amendment 1: an approximate value left two implementers free to pick different concrete numbers without contradicting the text). Not a blocking gap — `tech-analyst` can reasonably pin a concrete minimum without any product ambiguity — but worth naming so it's a deliberate deferral rather than a silent gap. **Fix guidance:** either state a concrete minimum on-print size now (e.g. "no smaller than Xcm / Ypx square on the printed A4 page"), or explicitly say "the exact minimum print size is a technical decision left to `tech-analyst`, constrained only by 'must not visibly pixelate or shrink below what a phone camera can reliably scan from ~1-2m'" — either is fine, the document currently does neither. |
| 3 | Non-blocking, optional | **QRL-05's "opening in a new tab is acceptable" is stated as a permission, not a requirement, leaving it ambiguous whether opening the print page in the *same* tab (navigating away from the modal/Events page entirely) would also satisfy the criterion.** The criterion's own stated rationale — "so the admin does not lose the modal's context" — is actually only true if a new tab is used; a same-tab navigation would lose that context, arguably violating the criterion's intent even though its literal text ("opening in a new tab is acceptable") doesn't forbid the alternative. This matters for a Cypress e2e assertion: should the test assert a new tab/window was opened (`cy.window().its('open')` spy, or an `href`+`target="_blank"` check), or just that *some* navigation to the print route occurred? As written, both are defensible readings. **Fix guidance:** one word-level tightening — e.g. "the print control opens the print page in a new tab (required, not merely permitted, so the modal's context — and the admin's place in the Events/Series table — is preserved)" — removes the ambiguity for both the implementer and whoever writes the Cypress assertion. |
| 4 | Non-blocking, optional | **QRL-09's defensive-behavior coverage for a missing `check_in_token` is scoped to "opens its QR modal (QRL-01) or clicks its copy-link control (QRL-07)" but doesn't say what the print page itself (QRL-04) should do if it is somehow reached (direct URL entry, a stale bookmark, a browser back/forward restore) for an item whose token is missing.** In the normal flow this is moot — per QRL-09, the modal's print control presumably wouldn't offer a working print action when the token is missing, so the print page is never reached via the UI in that case — but the print page is still a real, addressable route, and nothing in the document states its own behavior if loaded directly against a missing/invalid token (crash vs. inline "unavailable" message vs. redirect). This is a narrow, low-probability path (same trust/likelihood tier as QRL-09's own framing of the whole scenario as "a defensive guard against unexpected data, not an expected everyday case") but it is the one gap in an otherwise-complete defensive-behavior criterion. **Fix guidance:** one sentence extending QRL-09 (or a short addition to QRL-04) — e.g. "the print page independently applies the same missing-token guard if it is ever loaded directly (e.g. a stale bookmark or restored tab) for an item with a falsy `check_in_token` — same inline 'unavailable' treatment, no crash." |

## Testability assessment, item by item

- **QRL-01 (modal):** Testable as written — has an explicit Given/When/Then, names both pages, both trigger conditions, and the exact encoded URL shape. No gap.
- **QRL-02 (client-side generation):** Testable at the level the document targets (no network request during generation, legible at both on-screen and print sizes) — the "which library" question is correctly left open as a technical decision, consistent with this repo's existing pattern of deferring implementation choices that don't affect testable behavior (e.g. contract-markdown-rendering's CTM-09). No gap.
- **QRL-03 (absolute URL):** Testable and precise — concrete example format given, explicit statement that the origin comes from `window.location.origin` and not a new config value, which is itself a testable negative (grep/review-time check that no new env var was introduced). No gap.
- **QRL-04 (print page):** Testable for authentication-required, content (title + QR + same absolute URL as the modal), and print-trigger presence (auto or on-page button, not "menu-discovery-only"). The one soft spot is the sizing language (Finding #2, non-blocking/optional).
- **QRL-05 (print reachable from modal):** Testable, with one word-level ambiguity flagged (Finding #3, non-blocking/optional) about whether new-tab is required or merely permitted.
- **QRL-06 (generic copy button):** Testable — exact URL shape given (`{origin}/precheckin`, no `event_id`), placement described (header/toolbar, not per-row). No gap.
- **QRL-07 (per-event copy button):** Testable — exact URL shape given (`{origin}/precheckin?event_id={event.id}`), explicit non-goal for Event Series cross-referenced consistently with the document's own Explicit Non-Goals section. No gap.
- **QRL-08 (clipboard feedback):** Testable — both success and failure paths named, tied to the existing `showToast` API (so a Jest test can spy on it directly), explicit statement that failures must never be an unhandled rejection or silent no-op (a concrete, checkable negative). No gap.
- **QRL-09 (missing-token defense):** Testable and unusually well-grounded (the document independently verifies via the model definition that this is genuinely a defensive-only path, not a routine case) — one narrow scope gap (print-page-direct-access) noted as Finding #4, non-blocking/optional.
- **QRL-10 (responsive modal):** The criterion text itself is concrete and non-vague; the gap is purely in test-layer assignment, not in the requirement's clarity (Finding #1, worth folding in given `CLAUDE.md`'s blanket automated-test mandate, but does not block moving forward).

**Explicit Non-Goals / Constraints / Open Questions sections:** all consistent with the ten criteria, no scope-creep risk, no criterion left uncovered by them. The Open Questions section correctly identifies the only two genuinely-open technical choices (QR library, print-route shape) and correctly declines to treat either as product-ambiguous — confirmed accurate on independent review, not just asserted.
