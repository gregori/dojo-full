## Re-review (fixes verified against current diff)

1. **Frontend multipart `Content-Type` — RESOLVED.** `MedicalExamPage.tsx:43` and `StudentsPage.tsx:220` now set `headers: { 'Content-Type': undefined }` instead of the boundary-less static string. Traced through the installed axios (`node_modules/axios` — `AxiosHeaders.set`, `Axios.js:155` `AxiosHeaders.concat(contextHeaders, headers)`, `AxiosHeaders.toJSON`/`Symbol.iterator`): `set()` overwrites the instance default (`'application/json'`) with `normalizeValue(undefined)`, which is `undefined`; `toJSON()`/the iterator explicitly filter out entries where `value == null`, so the header is dropped entirely before `xhr.js` builds `requestHeaders` and calls `request.setRequestHeader(...)`. Net effect: no `Content-Type` header is sent at all, so the browser's native XHR `send(formData)` auto-computes `multipart/form-data; boundary=...` per spec. This genuinely fixes the root cause (not just changing the symptom) and is applied consistently in both call sites.
2. **Spoofable file-type check — RESOLVED.** `medical_exam_service.py`'s `_validate_file` (lines 60-65) now checks `content.startswith(signature)` against `MIME_SIGNATURES` (`%PDF-`, PNG's 8-byte signature, JPEG's `\xff\xd8\xff`) keyed by the declared `content_type`; an unrecognized or mismatched `content_type` is rejected (fail-closed), and a declared type whose magic bytes don't match is also rejected. This validation lives in the single shared `record_exam` method used by both the instructor endpoint and the public self-service endpoint (`_validate_file` is called once, inside the `if file is not None:` block, regardless of caller) — no divergent/bypassable path exists between the two upload routes. New test `test_rejects_spoofed_content_type_with_mismatched_magic_bytes` confirms an HTML payload declared as `image/png` is rejected with no `Document` row created. `make_upload()`'s default fixture content was also correctly updated to real PDF magic bytes (`b"%PDF-1.4 pdf-bytes"`), which is why the pre-existing supersession/history tests still pass.
3. **Unbounded read before size check — RESOLVED.** `_read_bounded` (lines 40-57) now reads in `UPLOAD_CHUNK_SIZE` (1MB) chunks via `file.file.read(UPLOAD_CHUNK_SIZE)`, accumulating `total` and raising as soon as `total > MAX_FILE_SIZE_BYTES`, before continuing to read further chunks. `record_exam` calls this instead of the old unconditional `file.file.read()` (line 124). Boundary check: a file of exactly `MAX_FILE_SIZE_BYTES` bytes is accepted (final chunk brings `total` to exactly the limit, not `>`, loop then reads an empty final chunk and exits cleanly); a file one byte over is rejected on the chunk where the running total first exceeds the limit, without reading the rest of the stream. New test `test_oversized_upload_is_rejected_without_reading_the_entire_stream` uses a custom streaming double (`_CountingStream`) reporting a 100MB declared size and asserts `stream.bytes_served <= 11 * 1024 * 1024`, directly proving the bounded-read behavior (max one chunk, i.e. ~1MB, past the 10MB limit — not the full stream).
4. **Supersession race condition — RESOLVED for the primary scenario; one narrow residual edge case remains (non-blocking).** `_get_active_record` gained `for_update: bool = False`, applying `.with_for_update()` before `.first()` when set; `record_exam`'s supersession path (line 142) now calls `_get_active_record(db, student.id, for_update=True)`. This lock acquisition happens inside the same session/transaction as the later `db.commit()` (line 159) — no intermediate commit occurs between the lock and the final commit (the earlier `db.flush()` for the new `Document` does not release the transaction). `database.py` has no isolation-level override, so MySQL's default `REPEATABLE READ` applies, and SQLAlchemy's `with_for_update()` is honored for MySQL (`SELECT ... FOR UPDATE`), so this genuinely serializes two concurrent requests **when a previous active record already exists** — the second request blocks until the first commits, then reads the now-superseded row and proceeds correctly. This is not decorative; it fixes the concrete failure scenario from the original finding.
   - **Residual, non-blocking:** when a student has **no** existing active record (first-ever submission), `SELECT ... FOR UPDATE` has no row to lock, so two fully-concurrent first submissions could theoretically still both observe `previous=None` and both insert `active` rows. In practice this is likely still mitigated on MySQL/InnoDB by next-key/gap locking on the `(student_id, status)` index (`ix_medical_exams_student_status`) under `REPEATABLE READ`, but that isn't exercised by any test (SQLite, used in the unit-test suite, does not support `FOR UPDATE` — SQLAlchemy silently no-ops it there) and would not hold under a `READ COMMITTED` isolation override. Suggested (non-blocking) follow-up: lock the parent `Student` row (`db.query(Student).filter(Student.id == student.id).with_for_update().first()`) at the top of `record_exam` to serialize unconditionally, independent of whether a prior `MedicalExam` row exists.

## Findings (ranked, most severe first)

### 1. [HIGH — Correctness, breaks AC1 and AC2] FormData uploads are sent with a boundary-less `Content-Type`, breaking multipart parsing in real browsers

- **Files:** `dojo-app/frontend/src/pages/MedicalExamPage.tsx:39-43`, `dojo-app/frontend/src/pages/StudentsPage.tsx` (`recordMedicalExamMutation`, the `api.post(..., { headers: { 'Content-Type': 'multipart/form-data' } })` call).
- Both upload call sites explicitly set `headers: { 'Content-Type': 'multipart/form-data' }` with no `boundary=` parameter, to work around axios defaulting `api`/`publicApi` instances to `Content-Type: application/json`.
- The comment's stated concern (axios would otherwise JSON-encode the FormData) is real and the override does prevent that — confirmed in `axios/lib/defaults/index.js`: `if (isFormData) return hasJSONContentType ? JSON.stringify(formDataToJSON(data)) : data;`. Because `contentType` is now `'multipart/form-data'` (not `application/json`), `hasJSONContentType` is false and the raw `FormData` is passed through.
- However, the browser's XHR adapter (the adapter actually used in a real browser — `axios/lib/adapters/xhr.js`) does **not** post-process or delete an already-present `Content-Type` header for `FormData` bodies; it just does `request.setRequestHeader('Content-Type', 'multipart/form-data')` verbatim, then `xhr.send(formData)`. Per the XHR spec, `send()` only auto-computes and appends the `Content-Type` (with the correct `boundary=...`) **if no Content-Type header is already present** in the request. Since axios already set one explicitly, the browser will send the literal header `Content-Type: multipart/form-data` with **no boundary**.
- (Axios's `fetch` adapter has explicit code to detect and strip a boundary-less `multipart/form-data` Content-Type so the browser can recompute it — see `axios/lib/adapters/fetch.js:271-279` — but the `fetch` adapter is not used here; axios's adapter order is `['xhr', 'http', 'fetch']` and XHR is used whenever available, i.e. in every real browser.)
- **Failure scenario:** A real user opens `/medical-exam` (public self-service) or an instructor opens the upload modal on `StudentsPage`, fills the form, and submits. The browser sends a multipart body with a `Content-Type: multipart/form-data` header lacking `boundary=`. FastAPI/Starlette's multipart parser cannot delimit parts without the boundary, so `registration_number`/`pin`/`exam_date`/`file` (all required `Form(...)`/`File(...)` params) fail to parse — the request either 422s or silently drops fields, and the upload never succeeds. This is not caught by any of the passed gates (`eslint`, `tsc`/`vite build`, backend `pytest`), because the backend tests exercise the FastAPI `TestClient` with `httpx`, which builds correct multipart requests directly from Python `files=`/`data=` dicts — they never go through the frontend axios/XHR code path at all.
- **Fix guidance:** Do not set a static `Content-Type` string. Either omit the `headers` override entirely from an axios instance whose default isn't JSON, or explicitly clear it so axios/the browser computes the boundary, e.g. `headers: { 'Content-Type': undefined }` (axios's `AxiosHeaders` treats `undefined` as "remove this header"), so the outgoing request has no `Content-Type` set beforehand and the browser fills in the correct `multipart/form-data; boundary=...` at `send()` time.

### 2. [HIGH — Security, weakens AC5] File type is validated only via the client-supplied `Content-Type` header — trivially spoofable, no actual content/magic-byte check

- **File:** `dojo-app/backend/app/services/medical_exam_service.py:33-39` (`_validate_file`).
- `_validate_file` checks `file.content_type not in ALLOWED_MIME_TYPES` — `file.content_type` is the `Content-Type` of the multipart part, which is fully attacker-controlled (the client sets it, e.g. via `FormData.append('file', blob, filename)` with an arbitrary `Blob` type, or a raw `curl -F "file=@payload.html;type=image/png"`). There is no inspection of the actual byte content (no magic-byte/signature sniffing, e.g. `%PDF-`, PNG's `\x89PNG`, JPEG's `\xFF\xD8\xFF`), and the filename extension isn't checked either — the extension is only used to build the storage key, not for validation.
- **Failure scenario:** An attacker (or a malicious/compromised student, since this endpoint is reachable via the public self-service upload with just registration number + PIN) uploads `evil.html` containing `<script>...</script>` with the multipart part's declared `Content-Type: image/png`. The service accepts it, stores it in OCI Object Storage under a `medical-exams/{student_id}/{uuid}.html` key (the `.html` extension from the original filename is preserved in the storage key — see `extension = Path(file.filename or "").suffix` at line 99), and persists `mime_type="image/png"` in the `documents` table even though the stored bytes are HTML. If any future feature (e.g. Phase 4 reuses this same `documents`/storage mechanism for contracts, or a document-download/preview endpoint is later added, as the plan explicitly anticipates) serves this object back — especially if it trusts the stored `mime_type` or lets the browser sniff content — this becomes a stored-XSS / content-type-confusion vector. AC5 ("only PDF/JPEG/PNG... are accepted") is not actually enforced against real file content, only against a header the caller fully controls.
- **Fix guidance:** Validate actual file content, not just the header — check magic bytes/signature (e.g. via `python-magic`/`filetype` or manual signature checks for the three allowed types) against the declared `content_type`, and reject on mismatch.

### 3. [MEDIUM — Security/availability, weakens AC5] Entire file is read into memory before the size limit is checked

- **File:** `dojo-app/backend/app/services/medical_exam_service.py:96-98` (`record_exam`): `content = file.file.read()` happens unconditionally, then `_validate_file` checks `len(content) > MAX_FILE_SIZE_BYTES` only afterward.
- **Failure scenario:** Both the public (unauthenticated beyond registration+PIN) and instructor upload endpoints accept arbitrarily large request bodies — nothing in FastAPI/Starlette or the visible app config caps request/body size before this code runs. An attacker submits a multi-GB file to `/api/v1/medical-exams/public/submit`; the full content is buffered into a Python `bytes` object in memory before the 10MB check ever rejects it. Repeated/concurrent requests (only rate-limited to 5 attempts/60s per IP+registration, which is easy to spread across registration numbers or wait out) can be used to exhaust server memory — a low-cost DoS vector on a public, credential-light endpoint. This is exactly the "zip-bomb/oversized-file handling before it hits size validation" risk called out in the review brief.
- **Fix guidance:** Enforce a size cap while reading (e.g. read in chunks up to `MAX_FILE_SIZE_BYTES + 1` and reject early), or set/enforce a request body size limit at the ASGI/reverse-proxy layer ahead of application code.

### 4. [MEDIUM — Correctness, weakens AC6] No locking around the "supersede previous active record" read-then-write — concurrent submissions can produce two simultaneously active `MedicalExam` rows

- **File:** `dojo-app/backend/app/services/medical_exam_service.py:115-134` (`record_exam`), using `_get_active_record` (lines 42-45) with a plain `SELECT ... WHERE status = 'active'` and no `SELECT ... FOR UPDATE`/serializable isolation. There is also no DB-level uniqueness constraint enforcing "exactly one active row per student" (by design, per the plan and the migration — `documents`/`medical_exams` only have a `CHECK` on the allowed `status` values, not a partial-unique index), so this is purely a service-layer invariant.
- **Failure scenario:** Two near-simultaneous submissions for the same student (e.g. the student double-taps "Enviar exame" on `/medical-exam` before the button disables, or an instructor and the student submit within the same window) each call `_get_active_record`, both observing the same (or no) `previous` row before either transaction commits. Both then set that same `previous.status = "superseded"` and `db.add()` a new row with `status="active"`, and both commit. Result: two rows with `status='active'` for the same student simultaneously, violating AC6 ("exactly one active record at a time") and corrupting the status/dashboard logic (`_get_active_record` uses `.first()`, so which of the two "active" rows is returned becomes non-deterministic on subsequent reads). Plan.md explicitly promises this is enforced "transactionally, same pattern used for `PreCheckIn` conversion" — worth noting `PreCheckInService.convert_for_attendance` (`pre_checkin_service.py`) has the same gap (no row locking), so this isn't a regression unique to this PR, but the plan's stated intent ("transactional... enforced") is not actually met by either implementation.
- **Fix guidance:** Wrap the read-modify-write in `db.query(MedicalExam).filter(...).with_for_update()` (or equivalent) inside the same transaction before superseding, so concurrent submissions serialize instead of racing.

Not currently reachable from the two existing endpoints, so non-blocking, but worth a defensive comment or assertion if this service method's contract widens later.
- Boundary-condition unit tests for `compute_status` don't test exactly-30-days-before-expiry or exactly-at-`expires_at` (the closest is `days=15` for `vencendo` and `days=-1`/`+1` for `vencido`/`valido`). I traced the logic by hand and it is correct at both boundaries (`>=` on both comparisons makes day 30 "vencendo" and the exact expiry instant "vencido", matching the plan's "more than 30 days" / "once past" wording), so this is a test-coverage gap, not a bug.
