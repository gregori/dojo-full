## Findings (ranked, most severe first)

### 1. [HIGH — Correctness/Reliability, breaks AC5/REP-05 for plausible business data] PDF export raises an unhandled exception (500) when a title-bearing field contains ReportLab-markup-special characters

`report_export_service.py:38-62` (`render_pdf_table`) passes `title` and each `section_title` directly into `Paragraph(...)` with no escaping. `api/reports.py`'s section builders interpolate DB-sourced free text directly into these titles, e.g. `f"Exame de Faixa - {report['student_name']}"` (line 155), `f"Presenças - {report['student_name']}"` (line 177), `f"Presenças - {report['event_type_name']}"` (line 199), and the section titles in `_class_attendance_sections`/`_financial_sections`. `Student.full_name`, `Event.title`, `EventType.name` are all free-text fields with no restriction against `<`, `>`, or `&` — set today by instructors/admins via `StudentsPage.tsx`/`EventTypesPage.tsx` with no such input restriction.

**Empirically reproduced** (scratch script against the actual `reportlab` version pinned in this project): `Paragraph("Exame de Faixa - <b>unclosed bold", styles["Title"])` raises `ValueError: Parse error: saw </para> instead of expected </b>` inside `reportlab/platypus/paraparser.py`, propagating all the way up through `doc.build(story)` uncaught by `render_pdf_table`, `reports.py`, or any FastAPI exception handler registered in `main.py` — this becomes an unhandled 500 for the caller. A balanced `<Test> & Co`-style string did *not* raise in isolated testing, but any of the very plausible dojo-naming patterns that include a bare `<`/`>` without a matching closing tag (e.g. an event/turma titled `"Aula <Avançado>"`, `"Turma A<>B"`, or a student/legal name containing a stray `<`) will 500 the belt-exam, student-attendance, and class-attendance PDF export endpoints. This is not a contrived adversarial payload — it is realistic, unremarkable input the endpoint must handle per AC5's "every report supports `format=pdf`... producing a downloadable file."

**Fix guidance:** escape all DB-sourced strings (`student_name`, `event_title`, `event_type_name`, and any other interpolated field) with `xml.sax.saxutils.escape()` (or an equivalent helper) before building any `Paragraph`-bound title/section-title string in `reports.py`/`report_export_service.py`. Add a regression test asserting `render_pdf_table`/the PDF endpoints don't raise for a title containing `<`, `>`, `&`, or an unbalanced tag-like substring.

### 2. [MEDIUM — Security, CSV/Formula Injection, CWE-1236] `render_csv` writes raw, unescaped cell values — the codebase's first-ever CSV export, with no existing escaping precedent to inherit

`report_export_service.py:24-35` (`render_csv`) writes each row's values via stdlib `csv.writer` with no neutralization of leading formula-trigger characters (`=`, `+`, `-`, `@`) or of characters that trigger legacy DDE execution in some spreadsheet clients. Several fields flowing into export rows are free-text set by staff with no character restriction: `Payment.method` (`reports.py:108`, "nullable string, informational only" per Phase 3's own design note), `ExamParticipant.override_reason` (not currently rendered in the CSV/PDF row builders, but present in the JSON response and the general risk pattern), `Student.full_name`/`Event.title`/`EventType.name` (rendered in every section). Because this is a brand-new capability (per `plan.md`'s own ground-truth note: "CSV export has no precedent" anywhere in this codebase), there was no existing escaping convention to reuse, and none was added.

**Impact:** if any of these staff-entered fields is later opened in Excel/LibreOffice/Google Sheets by an instructor/admin, a cell value beginning with `=`, `+`, `-`, or `@` can be interpreted as a formula (potential data exfiltration via `=HYPERLINK(...)`/`=WEBSERVICE(...)`-style formulas, or legacy DDE command execution in older Excel configurations). Lower severity than a typical public-facing CSV-injection finding because today's actors who can set these fields (instructor/admin via authenticated forms) are already trusted/authenticated — but it is still a real, standard CWE-cataloged gap for the report's intended consumer (an admin opening the exported file), and it is new attack surface this PR specifically introduces, not something inherited from an existing reviewed pattern.

**Fix guidance:** in `render_csv`, before writing each cell, if the string value starts with `=`, `+`, `-`, `@`, a tab, or a carriage return, prefix it with a single leading apostrophe (`'`) — the standard OWASP CSV-injection mitigation — or otherwise neutralize per the project's preferred convention. Add a regression test with a cell value starting with `=` and assert the written CSV cell is neutralized.

### 3. [LOW — test-coverage gap, non-blocking] No explicit 403 test for an authenticated-but-wrong-role caller

`test_api_reports.py::TestAuthorization` only asserts `401` for an unauthenticated caller on all four endpoints; there is no test asserting `403` for a logged-in user whose role is neither `instructor` nor `admin` (e.g., overriding `get_current_user` with a `student`/other-role `User` and expecting `403` from `get_current_instructor_or_admin`). Non-blocking: `get_current_instructor_or_admin` is shared, unmodified, already-tested code reused verbatim from Phases 2-4, and no IDOR/self-service path exists for reports (`Student` records are not `User` accounts and have no JWT-based login path at all, so there is no in-schema role that could exercise this gap in practice). Still worth adding for consistency with the epic's established authz-regression-test convention (e.g. PR-4's review point 4).

### 4. [LOW — observation, non-blocking] `app/api/reports.py` coverage is 85%, lower than the 100% on the two new service modules

Lines 71-82, 86-95 (some branches inside the `_belt_exam_sections`/`_class_attendance_sections`/`_financial_sections` row builders — likely the "no promotion"/"no override reason"/empty-field ternary branches) and 175, 197 (one branch each in the attendance/class-attendance route handlers, likely the pdf-vs-csv branch for one of the four endpoints) aren't directly exercised by a dedicated test. Not a defect — the behavior is simple, and the underlying `report_service.py` logic backing these branches is separately 100%-covered — just an observation that the export-formatting glue in `reports.py` itself has a few untested branches.
